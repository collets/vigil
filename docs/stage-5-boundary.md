# Stage 5 Docker boundary implementation

Docker Desktop's Linux engine is the selected WSL implementation candidate. Runtime controls and relay primitives are experimental until the qualification matrix passes with each actual harness/profile. Production readiness is still false.

## Process and filesystem layout

The trusted foreground controller owns project/coordinator databases, artifacts, Git effects and provider credentials outside the worker. The worker receives approved checkout paths, private native state, read-only protected Git/instruction mounts, an immutable executable image, a read-only controller lease, and a read-only mount of one provider socket. It receives no Docker/SSH agents, host credential homes or arbitrary host paths.

The container starts `vigil-guardian` as root PID 1, with capabilities dropped except SETUID/SETGID for launching a different non-root worker identity. `no-new-privileges` prevents the child gaining those privileges. The guardian observes a read-only controller lease (maximum ten-second horizon, checked every 100 ms) and an independent monotonic hard deadline (currently maximum 90 minutes). A failed/expired lease, deadline, signal or native-process exit terminates PID 1. Linux PID-namespace teardown stops detached descendants. Production cleanup must still confirm the engine reports a stopped, empty boundary and reconcile remote inference before releasing resource claims.

`vigil-worker` starts an ephemeral loopback-only HTTP listener inside a `network=none` namespace, then launches the native process with `OPENAI_BASE_URL` pointing there. Its transport can dial only the selected Unix socket. Other native provider routes must be disabled or explicitly rejected during profile qualification. The wrapper is not itself a sandbox and is not an alternate production entrypoint.

The Stage 5.1 planner protects top-level and explicitly enrolled ordinary nested repositories and instruction paths. Every ordinary ancestor of a nested protected path is self-mounted and sealed into the plan: it stays writable for implementation content, while worker rename/unlink of that mountpoint fails. The planner rejects unregistered nested repositories, replaced identities, symlink/hardlink aliases, linked worktrees, submodule Git files, external common-Git directories and nested filesystems before launch. The production launch path must still revalidate the plan and inspect the effective mounts after container creation.

## Provider relay

`internal/boundary.Relay` holds the actual API key. The worker gets a unique run-scoped token. The relay accepts only authenticated `GET /v1/models` (synthetic selected-model metadata) and `POST /v1/chat/completions` or `/v1/responses` for the exact selected model. It rejects noncanonical routes/query strings, redirects, unsupported request fields, duplicate JSON keys, hosted tools, background requests, multiple completions and provider-side storage requests. Only function tool definitions are accepted. Remote media is unsupported.

Limits: 8 MiB request body, 64 nesting levels, 16 MiB provider output, one in-flight request per relay, 30-minute transport ceiling. Output overflow or broken upstream streaming aborts the HTTP transport rather than reporting a clean end. Provider error bodies/cookies/auth headers are not forwarded. Proxy environment variables are ignored. Revoking the relay cancels its active transport and refuses subsequent calls, but does not prove remote inference has stopped.

The Unix-socket bridge passed a real WSL/Docker test using a network-isolated worker and a host synthetic provider. The actual provider key stayed outside the container; the worker's unauthorized model request never reached upstream. This topology is verified only on this WSL engine. On macOS OrbStack 29.4.0, the mounted host socket failed with connection refused, while filesystem and guardian cleanup primitives passed. The replacement VM relay now passes: a separate non-root relay process shares a socket volume read-only with the network-isolated worker. Its bounded, closed bootstrap arrives only on stdin. A root guardian controls its lease and hard deadline. Synthetic tests passed on both engines, including wrong-model denial and lease-loss revocation. Do not assume a Mac host Unix socket traverses the VM boundary.

The real Hermes gateway and one local model turn per platform pass through the WSL and OrbStack boundaries with pinned architecture-specific images and private native homes. Stage 5.1 also built and tested architecture-specific Codex images with private native homes, but did not submit a Codex turn: ChatGPT subscription authentication is not compatible with the current API-key relay, and neither unrestricted egress nor metered API fallback is permitted. Normal close and lease loss stop detached writers. These remain partial harness results because provider-idle proof and the production launch/submission recovery matrix are outstanding. See the results record for exact image and model identity.

## OrbStack host-provider route

On OrbStack, the VM relay forwards to a loopback host relay using `host.docker.internal`, the [documented Mac-host route](https://docs.orbstack.dev/docker/network). Only the VM relay has a bridge network; the worker retains `network=none`. No TCP ports are published. The host relay holds the real provider key. The VM relay receives only the per-run token on stdin, and its shared volume contains only the Unix socket. Synthetic tests exercised this full route, rather than assuming VM-to-host reachability from the shared-volume test.

The Mac live probe temporarily forwarded Mac loopback port 8080 over SSH to the existing Windows llama.cpp service reached from WSL. The credential was handed to the Mac test process through SSH stdin and stayed outside both containers. The tunnel closed after the one-turn experiment. This remains test orchestration: production cross-host capacity ownership, persisted identities, admission checks and crash reconciliation are not yet wired.


## Conservative checkout admission

`PlanCheckoutWithRepositories` admits one ordinary Git root and explicitly enrolled ordinary nested Git roots. It records each filesystem/common-Git identity and a bounded entry-metadata seal, derives and seals every nested protected-path ancestor, then revalidates them before generating mounts. It protects root and nested `.git`, `.gitmodules`, `AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md`, `GEMINI.md`, `.agents`, `.codex` and `.hermes` paths. Protected directories are mounted read-only recursively; ordinary ancestors are writable self-bind mountpoints for implementation and read-only for review. Discovery alone does not enroll a nested repository, and caller mutation of either list is rejected on validation.

The supported layout is one ordinary root with zero or more explicitly enrolled ordinary nested repositories on one filesystem. The planner rejects linked worktrees, external common-Git directories, submodule Git files, unregistered nested repositories, symlinks, hard links, special files, nested filesystems and more than 100,000 entries. Unsupported layouts need separate qualification; the planner never rewrites them. The metadata seal detects ordinary intervening edits and replacements; it is not a checkpoint content digest or exclusion against a hostile host process racing Docker. Production still needs coordinator ownership, mount inspection and checks at each journaled transition. Newly created paths require fresh admission before a subsequent run.

Real Git probes passed on Linux and OrbStack: approved root and nested work files remained writable for the implementation role; staging, empty commits, config/ref writes, alternate git-dir writes, raw metadata/instruction writes, protected-path ancestor replacement, new hard-link aliases and a local push from an independent clone into protected Git metadata all failed. A separate reviewer container could read the checkout but not write it. A new symlink into protected metadata did not permit a write. Existing aliases and unsupported layouts are rejected before mount creation. Repository identity discovery ignores ambient `GIT_*` overrides. `ValidateMountsForRole` compares effective mount sources by filesystem identity and rejects missing guards/protected mounts, wrong write modes, duplicates, shadows or unplanned mounts before start.


Actual controller SIGKILL probes now pass at pre-start, running-writer and observed-result fixture points on both engines. Workspace and endpoint quarantine survive; stopped-container evidence alone never releases them. The full persisted launch/result journal and uncertain-submission recovery matrix remain required before dispatch.

## Qualification and lifecycle evidence

Stage 5.1 stores immutable trusted qualification records keyed by the exact source, executable, image, boundary binaries, profile revision/configuration, tools, instructions, mount plan, runtime, platform, provider/model/effort, credential route, topology and endpoint/capacity authority. Each observation references a retained durable artifact whose kind, manifest metadata and content digest are verified before record admission and again during eligibility. Class-specific requirements match a structured class/name pair; a prefixed name from another class cannot satisfy them. Eligibility is `supported`, `unsupported` or `unverified` with reasons. User-authored profile capability declarations cannot create evidence, changing any bound input invalidates the previous record, and missing/corrupt referenced bytes fail closed.

Lifecycle evidence keeps worker state, containment emptiness, relay transport, submission delivery, per-route inference-capable native startup and provider state separate. The trusted caller supplies the exact qualified route set, and every route needs one boundary observation. Endpoint release requires a stopped worker, an empty boundary, a non-uncertain submission and independent proof that the provider is idle, unless durable evidence proves every expected route stayed before inference-capable startup. Missing routes, prompt non-delivery and a closed provider connection are insufficient. Competing WSL and Mac capacity owners for the same physical llama endpoint are rejected unless they use the same implemented cross-host authority.

Production dispatch remains disabled. The Stage 5.2 runner **does** persist stable run/resource identities, recheck eligibility immediately before the first effect, validate effective mounts after create, journal each launch phase separately, renew leases, and retain workspace/endpoint quarantine until the lifecycle release predicate passes. Two gaps remain, and they are what actually blocks production: **no production driver exists** (only `internal/supervisor/fixture_driver.go`), and **the full crash-point matrix has not been exercised live** across real harness/platform combinations. Only named recovery evidence from that matrix plus bounded live runs may create a production-launch qualification.
