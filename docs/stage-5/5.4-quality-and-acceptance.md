## Outcome and authority boundary

A task is accepted only by the core from current, immutable evidence for the exact repository set, plan/task/criteria revisions, check definitions, configuration, reviewer profile and instructions. The required sequence is actual checks, a distinct fresh read-only review, resolution of blocking findings, every manual `pass`, and any configured explicit human acceptance. A process exit, model statement, human waiver or exhaustion assessment cannot manufacture another gate's result.

Plan acceptance independently applies configured plan-wide checks, review, manual and human gates after every required task is accepted. Its service time is charged to the plan-services ledger. Success moves the plan to `finalizing`; it does not authorize a commit, push, draft request, publication or merge.

The authoritative quality path is new Stage 5.4 code. The provisional `quality_evidence`, `findings`, `manual_checks` and `acceptances` tables installed by migration 001 remain historical schema and are not silently promoted. Forward migrations 010–014 add the closed evidence records, correct inherited result-digest uniqueness, add bounded supervisor assessments, add durable quality budget segments/source reservations plus a comprehensive acceptance-authority epoch, and reconcile populated pre-v13 authority without editing historical migrations or digests.

## Dependencies and preserved invariants

The slice consumes, rather than replaces:

- Stage 5.1 exact profile/boundary/role eligibility and read-only reviewer mounts;
- Stage 5.2 repository enrollment, repository-set observations, durable effect/result/artifact journals, live owners, claims/fences and task/plan ledgers;
- Stage 5.3 stop/pause, checkpoint/recovery, repair attempt limits, cumulative accounting and exhaustion evidence;
- the artifact repository's durable content verification and the core command receipt/revision contract.

External process or model effects occur only after durable intent and outside a database transaction. Effect start atomically opens a durable budget segment. An executing effect with no terminal observation charges conservative unknown time, becomes uncertain, retains unresolved authority and is not automatically replayed. Fresh dispatch is blocked across every scope for that target until resolution. Every dispatch rechecks pause, owner/claim fences, revisions, definition/profile digests, budget and repository scope. Existing checkout bytes and unrelated branches are preserved. Check/review completion never accepts a task; only epoch-fenced acceptance can. Project-required checks remain unioned with task/plan additions. Synthetic fixtures never become production fallbacks; production check dispatch remains unavailable.

## Checkpoint B — actual checks and baseline exceptions

Dependencies: A plus a live owner holding all repository claims/fences. Endpoint capacity is not needed for a non-model check, but project ownership remains mandatory.

1. Add `internal/checks`. Preparation atomically rechecks task `checking` (or plan `verifying`), pause state, revisions, required-check union, definition digest, remaining task/plan-service budget and current scope, then persists a quality effect intent.
2. Admit only every-root-marked disposable fixtures; unsupported production/`qualified_runtime` dispatch fails before any effect. Run the exact approved argv without a shell in an agent-owned isolated copy with preserved file permissions and descendant-aware Unix containment. Set only the minimal environment plus approved variables and use the approved relative cwd. A host that cannot prove a detached descendant absent records uncertainty, retains ownership and blocks downstream gates.
3. Persist effect `executing` and its budget segment before process start. Bound combined stdout/stderr and inherited-output draining. Prove full process-group retirement before releasing claims. Verify the copied source equals the pre-copy source and remains unchanged after execution outside declared required-output paths. Record exit/timeout/interruption, overflow, outputs and evaluated authority. Missing, corrupt, truncated or mutated evidence cannot pass.
4. Re-fingerprint the real source before recording completion. Any mutation produces `source_mutated`, records both fingerprints and invalidates the attempted result. The isolated build tree is removed only when owned by the check runner; it is never evidence authority.
5. Charge the full durable effect interval to the existing task or plan-services ledger without resetting usage. Recovery charges an active crash gap as unknown, leaves the effect/source uncertain and blocks a new command across scopes. Paused projects cannot prepare or begin a new check.
6. Baseline exceptions are explicit immutable human authorities bound to one check definition, normalized failure identities, bounded paths, base repository-set fingerprint and rationale. A failing check remains visibly failing. Gate evaluation may classify only the exact authorized failures as `accepted_baseline`; an additional, changed or unclassified failure blocks. Exceptions never arise from model output or fixture results outside labeled tests.

Restart/failure behavior: `prepared` effects may start once after all authority is rechecked. `executing` effects with no observation become `uncertain` and require explicit reconciliation; they are not rerun. Artifact publication without result commit is safely discoverable by digest, but does not pass. Result commit without a readable artifact fails freshness.

Completion: implemented offline. Deterministic fixtures cover pass, nonzero failure, timeout, interruption, missing executable/output, overflow, original and copied-source mutation, background/inherited-output descendants, charged restart uncertainty, artifact tampering and an approved baseline plus a new failure.

## Checkpoint C — fresh review, findings and bounded repair

Dependencies: A–B, all required current checks gate-passing, exact review-role qualification and remaining budget.

1. Add `internal/review`. Review preparation creates a new run/effect and supplies a closed manifest: exact criteria and definition, canonical repository diff/fingerprint, current check records and baseline exceptions, and reviewer instruction/profile digests. The reviewer session/native identity must be nonempty, new, distinct from implementation and prior review sessions, and bound to the current scope.
2. Production review uses only an eligible Stage 5.1 review route and read-only checkout. Synthetic reviewers are accepted only for marked disposable fixtures and label their actor/session. Before/after fingerprints plus boundary evidence verify no repository write and no publishing authority. Any write attempt, profile mismatch, pause, malformed/partial output or artifact failure records a non-passing review.
3. Decode reviewer output with a closed versioned schema and unknown-field rejection. Validate bounded unique finding IDs, allowed severities, repository-relative locations, evidence text and result consistency. The application derives `blocking` from the configured threshold; reviewer-supplied blocking claims have no authority. Suggestions remain visible but do not require repair.
4. A blocking check/review/human rejection atomically moves the task to `needs_repair` and records the cause. Stage 5.3 `execution-followup-prepare --kind repair` remains the only implementation repair path. It preserves the same task ledger and repair counters. Any changed code creates a new quality scope; fresh checks and a fresh distinct review are mandatory.
5. Pending Stage 5.3 exhaustion may invoke one preauthorized bounded supervisor assessment. Reserve the exact task/exhaustion source before invocation; observed or uncertain reservations reject later command IDs without calling again. All paths charge the same ledger. Its closed result remains limited to `clarify`, `revise_or_split`, `eligible_reassignment` or `remain_blocked` and cannot weaken criteria or spending authority. Failure leaves a charged uncertain effect and the task blocked.

Completion: implemented offline. Malformed review data, reviewer write denial, stale evidence, suggestion-only approval, thresholds, bounded exhaustion assessment and persisted restart are tested. One disposable scenario completes rejection → repair → changed fingerprint → fresh checks → distinct fresh review.

## Checkpoint D — manual/human decisions and atomic acceptance

Dependencies: A–C and no unresolved/uncertain quality effect.

1. Add typed human commands for manual `pending|pass|fail|cannot_verify`, task `accept|request_changes|clarify|stop`, baseline exception, and plan equivalents. Every result binds evaluator, notes/evidence, exact scope and command receipt. Only explicit `pass` satisfies a manual criterion. A human-acceptance waiver changes only the human-decision requirement; it never creates a manual pass.
2. Criteria changes continue to require explicit human revision authority. A changed criteria digest retires earlier manual results/human decisions and records staleness. `fail` and `cannot_verify` route to repair/blocking according to the command without being treated as pass.
3. Task acceptance holds current repository claims while re-observing fingerprints, builds the final selected-gate manifest under the comprehensive authority epoch, and compares that epoch before/after reads and inside one immediate transaction. This covers state/revision, check union, artifacts, review/findings, manual/human records, budgets and unresolved effects. It writes that exact manifest and acceptance, or records rejected/raced. A competing WAL evidence commit at the gate-read/write boundary fails closed.
4. Accepted evidence is immutable. Later authorized criteria/definition/code change creates a new task revision or scope and retires current acceptance explicitly; it never rewrites the old record.
5. When all tasks are accepted, transition the plan to `verifying`. Plan-wide gates use the plan-services ledger. Plan acceptance re-observes every child task, requires a compatible non-invalidated acceptance, recursively revalidates its gates/artifacts under the same epoch, writes its manifest, and moves only to `finalizing`. It creates no delivery operation or grant.

Completion: implemented offline. Stale manual/human decisions, acceptance races, pause dispatch denial, task/plan ledger separation and no-delivery side effects are permanent tests. The end-to-end disposable scenario finishes with explicitly labeled fixture-human manual and acceptance actions; it is not real user acceptance.
