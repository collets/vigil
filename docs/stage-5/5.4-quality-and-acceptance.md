# Stage 5.4 — Checks, fresh review, repairs and acceptance

Status: implementation in progress; expanded 2026-09-22 from the independently accepted Stage 5.3 baseline `a182152` and acceptance handoff `4b48737`. Stage 5.3 R1–R10 are closed at the offline scope. Live production qualification is still incomplete and production dispatch remains disabled.

## Outcome and authority boundary

A task is accepted only by the core from current, immutable evidence for the exact repository set, plan/task/criteria revisions, check definitions, configuration, reviewer profile and instructions. The required sequence is actual checks, a distinct fresh read-only review, resolution of blocking findings, every manual `pass`, and any configured explicit human acceptance. A process exit, model statement, human waiver or exhaustion assessment cannot manufacture another gate's result.

Plan acceptance independently applies configured plan-wide checks, review, manual and human gates after every required task is accepted. Its service time is charged to the plan-services ledger. Success moves the plan to `finalizing`; it does not authorize a commit, push, draft request, publication or merge.

The authoritative quality path is new Stage 5.4 code. The provisional `quality_evidence`, `findings`, `manual_checks` and `acceptances` tables installed by migration 001 remain historical schema and are not silently promoted. Migration 010 adds closed, immutable records and upgrade tests without editing migrations 001–009 or their digests.

## Dependencies and preserved invariants

The slice consumes, rather than replaces:

- Stage 5.1 exact profile/boundary/role eligibility and read-only reviewer mounts;
- Stage 5.2 repository enrollment, repository-set observations, durable effect/result/artifact journals, live owners, claims/fences and task/plan ledgers;
- Stage 5.3 stop/pause, checkpoint/recovery, repair attempt limits, cumulative accounting and exhaustion evidence;
- the artifact repository's durable content verification and the core command receipt/revision contract.

External process or model effects occur only after durable intent and outside a database transaction. An executing effect with no terminal observation becomes uncertain and is not automatically replayed. Every dispatch rechecks the current project pause state, owner/claim fences, revisions, definition/profile digests, budget and repository scope. Existing checkout bytes, unrelated branches and nested enrolled repositories are preserved. Check/review completion never accepts a task; only the acceptance transaction can do that. Project-required checks remain unioned with task/plan additions. Synthetic fixtures never become production fallbacks.

## Checkpoint A — definitions, immutable scope and freshness

Dependencies: accepted Stage 5.3 migrations 001–009 and existing repository/config/profile snapshots.

1. Extend check definitions with a closed environment allowlist, required project-relative output paths and a bounded combined-output ceiling. Reject shell strings, ambient environment inheritance, absolute/traversing paths, duplicate keys/outputs and limits outside the enclosing attempt ceiling. Canonical definition digests include every field.
2. Add plan-wide criteria/check/reviewer/manual/human-gate configuration. Task manual functional gates are the criteria explicitly marked `manual`; setup `manual_prerequisites` remain readiness-only evidence and never enter the quality result set.
3. Add forward migration 010 containing:
   - immutable `quality_scopes`, binding plan/task revisions, criteria and definition digests, current config/check-set/profile/instruction digests and an ordered repository-set fingerprint manifest;
   - journaled `quality_effects` for `check`, `review` and bounded `supervisor_assessment` effects;
   - immutable check results, baseline exceptions, reviews, findings, manual results, human decisions, task/plan acceptances and acceptance attempts;
   - append-only staleness records containing a closed reason, prior/current scope or digest and detection time;
   - no-update/no-delete triggers for authority/evidence records and indexes for current-gate queries.
4. Centralize scope construction and freshness comparison in `internal/quality`. Evidence is fresh only when every relevant field matches and every referenced durable artifact re-verifies. Closed stale reasons are: repository content, plan revision, task revision, criteria, task/plan definition, project/check configuration, check definition/set, reviewer profile, reviewer instructions, artifact missing/corrupt, superseding result and explicit criteria retirement. Reordering alone changes neither task evidence nor its scope; relevant definition changes produce a new scope and an append-only stale record when old evidence is evaluated.
5. Repository-set fingerprints are canonical ordered manifests of every enrolled participant and its physical identity, repository revision, HEAD/ref, index/content digest, dirty paths and exclusions. Scope creation re-observes every repository and rejects an incomplete, substituted or mismatched set.

Completion: populated migration 009→010 upgrade and fresh-database tests pass; historical migration digests are unchanged; mutation of every scope input makes dependent evidence non-current with a recorded reason.

## Checkpoint B — actual checks and baseline exceptions

Dependencies: A plus a live owner holding all repository claims/fences. Endpoint capacity is not needed for a non-model check, but project ownership remains mandatory.

1. Add `internal/checks`. Preparation atomically rechecks task `checking` (or plan `verifying`), pause state, revisions, required-check union, definition digest, remaining task/plan-service budget and current scope, then persists a quality effect intent.
2. Run the exact approved argv without a shell in an agent-owned isolated copy of the enrolled source. Set an explicit minimal environment plus only approved name/value pairs, use the approved relative cwd, and give the check a fresh writable build/output tree. The managed source remains unchanged; nested repository boundaries and unsupported special files fail closed.
3. Persist effect `executing` before process start. Bound combined stdout/stderr without deadlocking. Record start/end, exit code or signal, timeout, caller interruption, overflow, required-output observations/digests and the evaluated source fingerprint. Publish the bounded output and result manifest through the durable artifact repository before committing the immutable check record. Missing, corrupt or truncated artifacts, missing/unsafe required outputs, overflow, interruption, timeout and source mutation cannot pass.
4. Re-fingerprint the real source before recording completion. Any mutation produces `source_mutated`, records both fingerprints and invalidates the attempted result. The isolated build tree is removed only when owned by the check runner; it is never evidence authority.
5. Charge actual active duration to the existing task ledger or plan-services ledger without resetting cumulative usage. A crash gap is unknown/charged according to the Stage 5.2/5.3 ledger contract. Paused projects cannot prepare or begin a new check.
6. Baseline exceptions are explicit immutable human authorities bound to one check definition, normalized failure identities, bounded paths, base repository-set fingerprint and rationale. A failing check remains visibly failing. Gate evaluation may classify only the exact authorized failures as `accepted_baseline`; an additional, changed or unclassified failure blocks. Exceptions never arise from model output or fixture results outside labeled tests.

Restart/failure behavior: `prepared` effects may start once after all authority is rechecked. `executing` effects with no observation become `uncertain` and require explicit reconciliation; they are not rerun. Artifact publication without result commit is safely discoverable by digest, but does not pass. Result commit without a readable artifact fails freshness.

Completion: deterministic fixtures cover pass, nonzero failure, timeout, caller interruption, missing executable/output, output overflow, source mutation, restart inspection, artifact tampering and an approved baseline failure plus a new failure.

## Checkpoint C — fresh review, findings and bounded repair

Dependencies: A–B, all required current checks gate-passing, exact review-role qualification and remaining budget.

1. Add `internal/review`. Review preparation creates a new run/effect and supplies a closed manifest: exact criteria and definition, canonical repository diff/fingerprint, current check records and baseline exceptions, and reviewer instruction/profile digests. The reviewer session/native identity must be nonempty, new, distinct from implementation and prior review sessions, and bound to the current scope.
2. Production review uses only an eligible Stage 5.1 review route and read-only checkout. Synthetic reviewers are accepted only for marked disposable fixtures and label their actor/session. Before/after fingerprints plus boundary evidence verify no repository write and no publishing authority. Any write attempt, profile mismatch, pause, malformed/partial output or artifact failure records a non-passing review.
3. Decode reviewer output with a closed versioned schema and unknown-field rejection. Validate bounded unique finding IDs, allowed severities, repository-relative locations, evidence text and result consistency. The application derives `blocking` from the configured threshold; reviewer-supplied blocking claims have no authority. Suggestions remain visible but do not require repair.
4. A blocking check/review/human rejection atomically moves the task to `needs_repair` and records the cause. Stage 5.3 `execution-followup-prepare --kind repair` remains the only implementation repair path. It preserves the same task ledger and repair counters. Any changed code creates a new quality scope; fresh checks and a fresh distinct review are mandatory.
5. Pending Stage 5.3 exhaustion may invoke one preauthorized bounded supervisor assessment, charged to the same task ledger and journaled like other external effects. Its closed result is limited to `clarify`, `revise_or_split`, `eligible_reassignment` or `remain_blocked`. It cannot change criteria, accept partial work, create gate evidence, increase budgets or authorize spending/model escalation. Assessment failure leaves the task blocked.

Completion: malformed/unknown review fields, duplicate findings, reviewer write denial, stale check manifest, reused reviewer identity, suggestion-only approval, blocking thresholds, repair exhaustion and persisted restart are tested. One disposable scenario completes rejection → repair → changed fingerprint → fresh checks → distinct fresh review.

## Checkpoint D — manual/human decisions and atomic acceptance

Dependencies: A–C and no unresolved/uncertain quality effect.

1. Add typed human commands for manual `pending|pass|fail|cannot_verify`, task `accept|request_changes|clarify|stop`, baseline exception, and plan equivalents. Every result binds evaluator, notes/evidence, exact scope and command receipt. Only explicit `pass` satisfies a manual criterion. A human-acceptance waiver changes only the human-decision requirement; it never creates a manual pass.
2. Criteria changes continue to require explicit human revision authority. A changed criteria digest retires earlier manual results/human decisions and records staleness. `fail` and `cannot_verify` route to repair/blocking according to the command without being treated as pass.
3. Task acceptance holds current repository claims while re-observing fingerprints, then uses one immediate database transaction to recheck project/plan/task states and revisions, current check union, artifacts, review/finding threshold, manual passes, configured human decision, budgets and absence of uncertain effects. It writes an immutable evidence manifest and acceptance, moves only that task to `accepted`, and records an acceptance attempt. A race hook must prove code, criteria, definition/profile or check changes between observation and commit fail closed.
4. Accepted evidence is immutable. Later authorized criteria/definition/code change creates a new task revision or scope and retires current acceptance explicitly; it never rewrites the old record.
5. When all required tasks are accepted, transition the plan to `verifying`. Plan-wide checks/review/manual/human gates use a task-null plan scope, the same freshness/effect rules and the separate plan-services ledger. Atomic plan acceptance rechecks every task acceptance and plan gate, writes its manifest, and moves the plan to `finalizing`. It creates no delivery operation or grant.

Completion: stale manual/human decisions, acceptance races for every authority dimension, pause dispatch denial, task/plan ledger separation and no-delivery side effects are permanent tests. The end-to-end disposable scenario finishes with explicitly labeled fixture-human manual and acceptance actions; it is not real user acceptance.

## Validation sequence

At each checkpoint run focused package/migration tests and commit a coherent local checkpoint. After integration run:

```text
make check
make check-race
make build
make build-boundary
make cross-build
```

Add new concurrent packages to `make check-race`. Default tests require no model, Docker, hosting, credentials or network. Run actual processes only in disposable repositories. For process/filesystem/locking changes, attempt native macOS arm64 validation on the previously authorized host using an isolated temporary exact-commit checkout/bundle, record commit and bundle SHA-256, and remove only created resources. If unreachable, record native validation pending; cross-build is not a substitute.

The completion demonstration must include one full synthetic cycle: implementation result at `checking`; failed check or rejecting review; bounded repair using the unchanged cumulative task ledger; fresh passing checks; distinct read-only review with only nonblocking findings; fixture-human manual passes and configured human acceptance; atomic task acceptance; plan-wide gates using the plan ledger; and transition to `finalizing`. Restart the database at least once during the cycle.
