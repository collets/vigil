## Outcome and dependencies

A task is accepted only from current, authoritative evidence: actual required checks, a fresh read-only review, resolved blocking findings, configured human acceptance and every required manual Pass. Failures lead to bounded repair or an explicit blocked decision. A model's claim of success cannot substitute for any gate. Original scope: B/G, with E's budget ledger.

Schemas and handler/fixture tests can proceed independently. Actual checks and model reviews require [5.1](5.1-execution-qualification.md), journaled execution from [5.2](5.2-repositories-and-execution.md), and safe repairs/recovery from [5.3](5.3-recovery-and-controls.md). [5.5](5.5-workflow-and-planning.md) renders the resulting evidence and decisions; [5.6](5.6-delivery-and-finalization.md) consumes acceptance without conflating it with commit authority.

## Work checkpoints

### A. Quality records and freshness rules

- [ ] Add immutable check, review, finding, manual-result, human-decision and acceptance records bound to repository-set fingerprint, task/criteria revisions and relevant definition/profile/instruction digests.
- [ ] Centralize invalidation: code/dependency/criteria/check/profile changes invalidate affected downstream evidence and pending decisions; harmless reorder/narrative edits do not erase unrelated evidence. Record why and which records became stale.
- [ ] Keep project-required checks unioned with task additions. A task/model cannot remove required checks or weaken ceilings. Closed result schemas treat model fields as claims pending validation.

### B. Actual contained check runner

- [ ] Execute only approved argv/cwd/environment/time definitions through the qualified boundary and journal. Capture exit/timeout/interruption, start/end, bounded output artifact, required output presence and evaluated fingerprints. Native/model “tests passed” text is never authoritative.
- [ ] Define how writable build output is isolated and detect source mutation during checks. A check evaluating or modifying a different source fingerprint cannot approve the earlier one; re-fingerprint and block/re-run through policy as necessary.
- [ ] Enforce task cumulative budget and termination/resource cleanup. Missing executable/output, truncated evidence, interrupted execution or corrupt artifacts cannot become a pass.
- [ ] Add explicit baseline-failure authorization bound to check, normalized failure identity, paths, base fingerprint and rationale. Matching accepted baseline stays visibly unhealthy; new/unclassified failures block.

### C. Fresh review and bounded repairs

- [ ] Launch a new read-only reviewer session with accepted criteria, exact diff/fingerprint, check evidence and baseline failures. Verify no code or publishing access, and record the distinct native identity. Invalid/partial review is not approval.
- [ ] Validate finding IDs, severity, locations and evidence. Keep suggestions visible without requiring repair; apply configured blocking thresholds deterministically.
- [ ] Route rejection/request-changes to `needs_repair`; charge a new implementation attempt to remaining cumulative allowance, use 5.3 preservation rules, and invalidate changed-code evidence before rechecking/reviewing.
- [ ] On exhaustion, allow only a preauthorized bounded fresh supervisor assessment. It may propose clarification/revision/split/eligible reassignment; it cannot relax criteria, accept partial work or authorize a stronger paid model.

### D. Human/manual and plan acceptance

- [ ] Expose typed human actions: request changes, clarify requirements, stop task and accept where gates allow. Criteria changes require an explicitly identified human revision and retire stale approvals.
- [ ] Store manual `pending/pass/fail/cannot_verify` with evaluator, notes/evidence and evaluated fingerprint. Only Pass satisfies the gate; a human-acceptance waiver never creates manual Pass. Default code-change behavior invalidates manual evidence.
- [ ] Implement atomic task acceptance rechecking every current gate and revision. Test races between acceptance and code/definition changes. Keep task commits separate from acceptance.
- [ ] Add plan-wide checks/review/manual acceptance and the transition into finalization after all required tasks are accepted. Charge plan services to the separate ledger; never recursively accept or finalize via model claims.
