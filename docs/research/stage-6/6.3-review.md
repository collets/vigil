### The gate

Round 13 first observed that `TestDocsNextActionRangeIsCurrent` cannot catch this
class: it fires only on literal `a..b` ranges in `status_documents`, while these
counts live in prose. Rounds 14 through 18 each re-derived that same conclusion
from a fresh failure. The remedy is now built rather than noted.

`internal/doccheck/remediation_count_test.go` counts the remediation commits after
the rejected candidate from the git history, derives the reviewed, outstanding and
total-row counts from them, and asserts three specific claims here: the applied
count in the status line, the outstanding ordinal in the status line, and the
outstanding ordinal in the closing section. Each is matched against its own
sentence, because an earlier draft of the gate tested bare substrings and passed
on a number that happened to appear inside a historical finding — the same weak
assertion in a different place. It also asserts the pending row names the
outstanding ordinal, and that the rounds table carries exactly one row per review
plus one.

This is the first finding in this stage closed by a mechanism rather than by
care. Five consecutive rounds of prose discipline over the same sentence did not
manage it once, and the sixth would not have either.

**What the gate does not check, stated so it is not over-trusted.** It verifies
countable claims against the commit history. It does **not** detect R18F2 — an
earlier remediation editing this record's past finding text so the numbers would
agree. That is a change to prose, and a count gate can only see prose whose value
it knows how to derive: mutating R16F1's text back to "six/sixth" leaves the gate
green, which was verified rather than assumed. That finding needs a reviewer, and
will keep needing one.

**Five remediations exist for round 18, and the reason is the gate's own
history.** `879b435` carried the round-18 fixes and the gate; `52f3d29` fixed two
defects in that gate; `aab834e` corrected the invariant it had falsified and
spelled the counts for the commit it became; `a19fb64` inverted the gate's commit
classification after it under-counted the commit that introduced it; `3b1f959`
recorded that sequence and spelled the count for the commit it became. All five
answer round 18 and all five are counted, because squashing them would mean
rewriting history this branch has already published.

That sequence is worth stating plainly rather than hiding: **each fix was a new
commit, and each new commit was the thing the gate then caught.** It is the
clearest possible demonstration of the loop this gate exists to close, and of why
closing it needed a mechanism rather than care.

**The gate was verified by mutation, not by reading.** Setting the applied count
to a number the history does not support fails it; setting it to the number the
history does support passes. The same mutation against R16F1's finding text is
invisible to it, which is the limitation stated above rather than a guess.

**Three defects in the gate itself, each found by the gate failing on the commit
that introduced it** — which is the only evidence that a gate like this works. It
first compared a cardinal against an ordinal, so "ten remediations applied" was
reported as needing to read "tenth". It then assumed exactly one review per
remediation, which its own existence falsified. And it classified commits by
enumerating remediation subject prefixes, so the commit that introduced the gate
was not itself counted — a whitelist of inclusions that failed toward
under-counting the thing it measures. The classification is now inverted: every
commit after the rejected candidate counts except three named bookkeeping
commits, because a closed list of exclusions fails toward the opposite, safer
error than a list that must be extended before it sees a new subject.

## What these rounds establish, and what they do not

Eighteen rounds is not eighteen independent opinions on the finished slice.
Rounds 1–8 reviewed a **checkpoint** each; rounds 9–18 reviewed the **assembled
candidate** and remediations 1–9. Every P0 and P1 returned across all eighteen
rounds is fixed in the tree, but the **fourteenth** remediation has not itself
been independently reviewed, so 6.3 is not accepted.

The finding class was remarkably consistent: **a claim outrunning the code
beside it**. Round 1's remediation for "wall budget consumed cannot be rendered"
added the field from a table with no writer, which is the most consequential
instance of it — the fix satisfied the reviewer's wording while breaking the
property the finding was about. Round 9's fourth finding is the same shape in
documentation: a test asserting the absence of a clause that the requirement it
certifies explicitly demands.

What this suggests for later sub-stages, and it is the one durable lesson here:
**eight clean checkpoint reviews did not predict the assembled candidate.** Each
checkpoint was reviewed against its own boundary, and each boundary hid a defect
that only the seam could expose. The per-checkpoint verdicts should be read as
"this checkpoint is sound in isolation", never as "this slice is sound".

And the class outran the medium. The same failure — a written claim outrunning
the code beside it — appeared in SQL at round 1, in a test's assertions at round
9, and in **prose in the evidence document** at rounds 10 and 11. Round 10's
blocking finding was an evidence row rewritten to a string the measured commit
cannot produce; round 11 found the same shape again in the width figure beside
it, and a review record that contradicted its own header because the header had
moved on and the closing paragraph had not. **Documentation written *after* the
code is where this repository's claims drift most easily**, and a count or a
string copied into a status paragraph a round ago will be stale a round later
without anything failing to tell you.
