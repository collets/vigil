## Outcome and dependencies

Give the interface the execution lifecycle. The register assigns 6.6 **ten
rows**: `execution-prepare`, `execution-start`, `execution-inspect`,
`execution-reconcile`, `execution-stop`, `execution-resume-prepare`,
`execution-followup-prepare`, `checkpoint-save`, `checkpoint-clear` and
`checkpoint-restore`. Nine of them have no interface surface at all, and
`execution-stop` exists only as the bare `s` key — which can only stop a run the
interface has no way to create.

6.6 adds **no new product capability**. Every command it exposes is already
implemented and already fixture-gated; 6.6 must not widen any gate.

Depends on 6.2's screen stack, confirmations and bounded text entry, 6.3's run
read model, 6.4's recovery observation form, and 6.5's budget and evidence
views.

## Invariants 6.6 must not break

1. **The interface never launches a model implicitly.** Every execution action
   is an explicit, confirmed operator action. `execution-prepare` persists
   without launching; `execution-start` is a separate deliberate act.
2. Fixture-only drivers stay fixture-only. `execution-prepare`,
   `execution-start`, `execution-stop`, `execution-reconcile` and
   `execution-recovery-choose` require `--synthetic-fixture` in the CLI; the
   interface must not offer them for a non-synthetic run, and the screen must
   say why they are unavailable.
3. `--single-host` remains required. The interface must not present
   cross-instance capacity as coordinated.
4. An uncertain submission is never resubmitted. The allowed-next-command set
   is rendered, and the interface must not offer an action the set excludes.
5. Reconciliation never turns an over-budget terminal observation into success,
   and never moves a local ref or POSTs a draft.
6. Checkpoint clear derives agent-owned paths only from the validated execution
   result. The interface must not gain a free-form path field, and
   `checkpoint-restore` stays an explicit approval bound to all three set IDs
   and the current revision.
7. Existing user work is never discarded. Clear and restore both require the
   confirmations 6.2 introduced and both show the exact participating
   repositories before acting.
8. Budgets are never reset. The interface shows remaining, charged and unknown
   time, and the excluded approval/resource wait segments.
9. Production dispatch stays disabled. 6.6 renders the closed gates; it does not
   open one.

## Work checkpoints

### A. Execution list and detail

- [ ] Execution list per task: every attempt, its kind, state, generation,
      runtime kind, wall/active charge, unknown charge and outcome observation.
- [ ] Execution detail for one run: the prepared intent, the delivered prompt
      generation, the effect journal, the writer-observation state, the
      uncertainty state and its reason, and **the allowed next commands** with
      the ones that are refused and why.
- [ ] The detail screen must make P11 explicit: a completed process is not an
      accepted task. It must also make the separation between
      `prepared`, `executing`, `outcome observed` and `result persisted` visible,
      because that is where lost work is decided.

### B. Prepare and start

- [ ] `execution-prepare`: show the consumed dispatch, the rechecks that will
      happen (project state, revisions, dependencies, profile, policy, budget,
      repository authority) and the absolute wall limit, then confirm.
- [ ] `execution-start`: select the repository and path from the **enrolled
      repository and the task's accepted scope**, never from free text; show the
      bounded content and instruction; show that a re-submission is refused for a
      durably delivered generation; and require an explicit confirmation that
      this is the deliberate start of an external effect.
- [ ] A screen-level precondition: the runtime gates are shown as closed, with
      the exact issue text, before the operator reaches a start action they
      cannot use. R70's honesty requirement applied to execution.

### C. Stop, inspect and reconcile

- [ ] `execution-stop`: the two grace values become visible, editable
      defaults rather than 2 s/5 s constants; the container state and the
      containment intent are shown before the interrupt; the post-stop
      writer-observation proof is shown after it.
- [ ] `execution-reconcile`: the expected repository and path are **selected
      from the run's validated result set**, so a substituted path cannot be
      submitted; the reconciliation's non-replay guarantee is stated on screen.
- [ ] Both are confirmed through 6.2's confirmation step with the displayed
      revision and run ID.

### D. Recovery

- [ ] Link the 6.4 recovery observation form to the run it targets, so the
      operator can see the session identity, the destination checkpoint and the
      generation before choosing a mode.
- [ ] `execution-resume-prepare`: show the exact-resume generation's identity
      and workspace authority, and that a replacement prompt is refused.
- [ ] `execution-followup-prepare`: the three kinds — `repair`,
      `infrastructure`, `fresh_context` — are distinct selections with their
      distinct preconditions. Show that repair and infrastructure retries do
      **not** reset cumulative charge, and that infrastructure additionally
      requires proof that no prompt or tool effect was delivered.
- [ ] Show the choice record that links a follow-up attempt to its recovery
      choice and bound checkpoint.

### E. Checkpoints

- [ ] Checkpoint set list per run: ID, kind (baseline, captured, destination),
      coverage over every participating repository, state, and creation time.
- [ ] `checkpoint-save`: non-destructive by construction; the screen must say
      that saving never clears anything, and list the repositories it will
      cover before it runs.
- [ ] `checkpoint-clear`: show the derived agent-owned path set, the baseline it
      is verified against, and the post-result fingerprint check. No free-form
      path. Already-confirmed paths cannot be overridden.
- [ ] `checkpoint-restore`: an explicit approval bound to the three visible set
      IDs and the displayed revision. Show the destination snapshot, the
      conflict state if any, and the journal. State that a conflicted or
      interrupted restore means **not** discarding any checkpoint, and that the
      identical command must be repeated only while the destination still
      matches an expected or already-applied state.
- [ ] Per-path journal view: every path, its journal state and the last
      recorded outcome. This is what makes "repeat the identical command" an
      informed decision rather than a guess.

### F. Budgets and retry accounting

- [ ] Per-task and per-plan ledgers: active allowance, charged, unknown, and the
      excluded approval and resource wait segments, with the generation
      breakdown for exact resumes.
- [ ] Retry-class counters: repairs, infrastructure retries, fresh-context
      attempts, and task-cumulative exhaustion. R55 and R61 require the classes
      to be distinguishable, and R18's escalation must be shown as a pending
      supervisor assessment rather than an automatic retry.
- [ ] Show exhaustion blocking progression rather than silently stopping.

## Autonomy and user gates

Autonomous: everything, for the labelled disposable-fixture paths, which is how
Stage 5.2/5.3/5.7 qualified these same commands. `make scenario` already walks
them; 6.6 re-walks them **through the interface** and records the evidence.

User gates: a real harness turn, a real interrupt, a real restore of a real
checkout, and native macOS evidence. All are **Stage 8's** or blocked on
authentication. 6.6 must record partial evidence with the exact missing step
rather than calling the walkthrough complete.
