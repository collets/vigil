## How this was measured

Two independent sources, as the scope document requires:

1. **Reading the code.** `internal/tui` is one 700-line file with a single
   `View()`; `internal/core/dashboard.go` is the only thing that feeds it;
   `internal/cli/project.go` and `internal/cli/root.go` are the only
   product entry points.
2. **Exercising the built binary.** A disposable marked fixture repository was
   registered with `vigil project init`, seeded through the production command
   path (`project.configure`, `profile.put`, `spec-import`, `plan.put`,
   `proposal-create`), and the real `vigil dashboard` binary was driven
   inside a 110×40 PTY at each of its five views. Individual keys were pressed
   and the resulting persisted state was re-read through `vigil project status`.
   At 60 and 40 columns the same binary was driven again to measure truncation.

Nothing below is taken from the interface's or the CLI's self-description. Where
this document and [`stage-5-cli.md`](../stage-5/stage-5-cli.md) disagree, the
binary won and the discrepancy is recorded as a finding.

### 2.2 Classification rule

Each entry gets exactly one classification, and the rule is mechanical so a
reviewer can re-derive any row:

- **E — expressible.** The interface can perform the same capability with the
  same information, choosing it from what the interface displays. **A bounded
  free-text field is not a compromise** — the interface already has one — and
  neither is *restricting* what the operator may supply, such as selecting
  citations from a validated set instead of typing them. Both spare the operator
  from supplying something the interface already knows or cannot verify.
- **C — expressible with a documented compromise.** The capability is
  reachable, but the operator must supply something the interface cannot
  display, select or verify, in one of exactly three situations: (a) a
  filesystem path outside the interface's own state, (b) a **nested or
  recursive** closed document it must build through a guided editor — a flat
  list of scalars in a guided form is `E`, not `C` — or (c) a private key file.
  Each C row names which of the three it is, in those words. The nestedness
  qualifier is load-bearing: without it `quality-review` (a flat review result
  in a guided form, `E`) and `project.configure` (whose `check_definitions` is
  a flat argv list nested inside a policy document, `C`) would sit on opposite
  sides of an unstated line, and a reviewer could not reproduce the split.
- **X — excluded, with reason.** The capability is not reachable from a
  terminal interface, or Stage 6's scope deliberately excludes it. Each X row
  names which of those two reasons applies. **No row is currently excluded for
  technical impossibility**: all six are either shell or subprocess mechanics
  an operator has no business driving, or scope decisions the user has already
  made. The **closed exclusion list in `requirements.md` has eight entries**,
  six of which are these rows; the other two — code/diff inspection and
  automatic merge — name capabilities rather than commands, so they have no
  register row. The list is a strict superset, and that is stated there too. The two reason classes are kept apart deliberately, because only a
  scope decision would justify revisiting the scope.

The full 85-row register is
[§4 of the results document](../../research/stage-6/results.md#4-parity-register).
Its totals:

| Class | Count | Share |
| --- | --- | --- |
| E — expressible | 67 | 79% |
| C — expressible with a documented compromise | 12 | 14% |
| X — excluded, with reason | 6 | 7% |

## 3. Requirement audit

Audited: R11, R45, R46, R47, R70, as the scope document directs. Verdict is one
of (a) met, (b) partially met, (c) not measurable as written. For (b) and (c)
the requirement text and the verification conditions were amended in the same
change; see [`core/requirements.md`](../../core/requirements.md) and
[the requirement map](../stage-5/stage-5-plan.md#complete-requirement-map).

### R11 — "Make the dashboard the primary application interface, with ways to intervene in individual agents."

**Verdict: (c) not measurable as written, and (b) partially met.**

Why it is not measurable: "the dashboard" never says whether it means the
terminal interface alone or the terminal interface plus the CLI; "primary"
names no comparison; "ways to intervene in individual agents" does not enumerate
the intervention points, so "enough" has no boundary. Nothing in it can fail,
which is why an interface expressing 4 of 82 capabilities has sat under it for two accepted stages.

Why it is partially met: 4 of the 82 distinct capabilities are fully expressed.
The interface cannot create a project, cannot define a profile, plan, task,
repository, check or restriction, cannot see a repository, run, checkpoint,
delivery, archive, artifact, reservation or resource claim, and cannot reach
the `resources` tree at all. Seventeen product capabilities have no interface
surface of any kind.

**Amendment made.** R11 now requires a reachable path for every persisted
product capability except those in **the closed exclusion list recorded in
[`requirements.md`](../../core/requirements.md) itself**, and a distinct
revision-bound action for every human decision point rather than a fallback to
the CLI. The list lives in the requirements baseline rather than in a Stage 6
deliverable so that the executing agent cannot satisfy the condition by writing
its own register; that reduces self-certification without eliminating it, and
both `requirements.md` and 6.2 now say so rather than overclaiming. P13 and P14 make it mechanically checkable:
every leaf command and envelope kind must be classified, and every decision
class must have its own action bound to the visibly displayed exact revision.

### R45 — "Prioritize task progression and actionable user requests on the main dashboard; show compact quality status and optionally live agent activity."

**Verdict: (b) partially met, and (c) not measurable as written.**

Why it is not measurable: "prioritize" states no ordering; "actionable user
requests" states no bound or selection rule; "compact" states no content;
"optionally" makes the whole activity clause uncheckable, and "live" does not
say what is live or from which source.

Why it is partially met, measured:

- The main view shows no active plan, no current task, no blocker, no queue
  position and no compact quality status. Those exist only in the Tasks and
  Detail views, so progression is not what the main dashboard prioritizes.
- Actionable requests are reduced to a **count**. The list is on view 3.
- `DashboardSnapshot.ActiveRun` is selected from the database and **never
  rendered in any view**; it is consumed only by the `stop` mutator. There is
  no live run, session or agent state on screen at all, so nothing about agent
  activity is observable.
- `DashboardSnapshot.Queue` is likewise read and **never rendered**; `u` queues
  the first queueable plan found in the snapshot without showing which one.

**Amendment made.** R45 now names the eight things the main screen must show
without navigating away, and defines agent activity as a bounded sanitized view
of persisted run/session/event state rather than raw harness output. P15 makes
it a cold-start assertion.

### R46 — "Put detailed changes, quality results, and cost information in secondary navigable views."

**Verdict: (b) partially met, and (c) not measurable as written.**

Why it is not measurable: "detailed", "secondary" and "navigable" name no
depth, no hierarchy and no focus rule; "cost information" names no source.

Why it is partially met, measured:

- The Detail view is a single flat list, not navigable: there is no focus that
  opens a finding, a check result, an artifact or a task. `h`, `m` and `t` act
  on the focused task, but nothing else is reachable.
- "Detailed changes" is rendered as the literal string
  `Detailed diffs remain external.` and nothing else. R47 correctly puts diff
  inspection in an external IDE, but the change *record* — paths, artifact
  references, commit references — is also absent, even though
  `execution_results_v11.changed_paths_json` and
  `repository_fingerprints_json` hold exactly that and are already written. So
  the requirement has no in-application meaning at all despite having a
  persisted source.
- Reviewer findings are a **count**. Finding severity, blocking status and text
  are persisted (`quality_findings_v2`) and never read by the interface.
- Check results are the string `check_id:status:output_artifact_id`. Exit state,
  bounded output and evidence reference are not shown.
- There is **no cost or usage surface in the interface** — not in the TUI and
  not in the core's read model. `grep -c 'cost\|usage\|token'
  internal/tui/dashboard.go` is `0`, and `internal/core/dashboard.go` never
  selects from `usage_observations`. The **capability exists and is
  implemented**; the view is simply missing. See §6 for the correction of an
  earlier draft that generalised this absence to the capability. P07 already
  requires that unknown never be shown as zero, so the honest reading is that
  the interface must render the persisted values where they exist and an
  explicit "unavailable" state where they do not.

**Amendment made.** R46 now names change *records* rather than diffs and requires
navigation from a visible focus. **The cost/usage clause is left exactly as
written** — an earlier draft appended an "explicitly unavailable" escape clause
to it, which would have made the requirement permanently satisfiable by an
absence notice and therefore deleted it in all but name; that was reverted, and
§6 explains why. The honesty obligation lives in P07 (pre-existing) and P16
(new), which govern the **view** and must never be used to excuse a missing
**capability**. The capability is not missing: see §6.

### R47 — "Show reviewer findings, implementation summaries, and check results in human review; use external IDE tools for code/diff inspection."

**Verdict: (b) partially met, and (c) not measurable as written.**

Why it is not measurable: "show" names no depth; "in human review" does not
identify which surface is the human-review surface, and the interface has none;
"implementation summaries" are never defined as to content or provenance.

Why it is partially met, measured:

- There is **no human-review screen**. `h`, `m` and `t` are the review actions,
  but the operator presses them against a task row without ever being shown what
  is being accepted.
- Reviewer findings are two integers. No severity, no blocking status, no
  text, no location.
- Check results are three colon-separated fields joined into one string.
- **The implementation summary is persisted but never read by the interface.**
  `execution_results_v11.summary` is written at
  `internal/supervisor/runner.go:1120` and read back by
  `internal/supervisor/reconcile.go:167`, but `DashboardSnapshot` exposes no
  field for it and no view renders it. The History view renders only an event
  kind label.
- "Use external IDE tools" is honoured, and the interface says so — that part is
  met and is the one part of R47 that is currently correct.

**Amendment made.** R47 now names, per item, what must be visible: each
finding's severity, blocking status and text; the implementation summary for the
current attempt; each check's status, exit state and evidence reference; and an
explicit statement of where to look for code and diffs. P17 is the acceptance
condition, and **P17 requires the implementation summary to render** — read from
`execution_results_v11`, not synthesised. An earlier draft omitted it from P17
and recorded the capability as a missing product gap; both were wrong, and §6
records the correction.

### R70 — "Provide a terminal-only interface initially; defer a browser dashboard."

**Verdict: (a) met as written, and (c) not usable as a parity criterion.**

Met: no repository process serves a web or network interface, and every
interactive surface is a terminal program. R70 constrains *form*, and the form
is correct.

Not usable as a parity criterion: it says nothing about completeness, so it can
never fail and cannot detect a four-capability gap. The risk is that "terminal-only"
is read as a licence to be incomplete.

**Amendment made.** R70 keeps the form constraint and adds the measurable half:
no repository process serves a browser or network UI, **and** the interface's
completeness claim is backed by the Stage 6 feature list rather than by the
absence of a browser. P18 is the acceptance condition.

## 6. Correcting two claims this analysis originally got wrong

An earlier draft of this section asserted that the application observes **no cost
or usage** and persists **no implementation summary**, and filed both as product
gaps outside Stage 6's scope. **Both assertions were false, and both were caught
by checking the installed schema rather than the interface.** They are recorded
here because the error is instructive: the first draft grepped the TUI for
`cost`, found nothing, and generalised from the absence of a *view* to the
absence of the *capability*.

| Claimed product gap | What the repository actually contains | Correct classification |
| --- | --- | --- |
| "No cost or usage model exists" | `usage_observations` is in the installed schema (`project-001.sql:104-110`) with nullable `input_tokens`, `output_tokens`, `cached_tokens`, `cost_microunits`, `currency` and an `observed`/`estimated` `provenance` — exactly what [core-spec §11](../../core/core-spec.md) requires. It is **written** at `internal/supervisor/runner.go:993` from the harness's reported usage and **read** at `internal/core/finalization.go:532`, where it reaches the factual archive. | **Not a product gap. An interface gap.** The data is persisted and queryable; `internal/core/dashboard.go` never selects from it and `internal/tui` never renders it. Owned by 6.5 as an ordinary register row. |
| "No persisted implementation summary" | `execution_results_v11` carries a per-attempt `summary TEXT NOT NULL` alongside `changed_paths_json` and `repository_fingerprints_json` (`project-004.sql:68`, carried forward by `project-011.sql:11-20`), and is written at `internal/supervisor/runner.go:1120`. `internal/supervisor/reconcile.go:167` already reads the summary back. | **Not a product gap. An interface gap.** R46's "change records" and R47's "implementation summary" both have persisted sources; the interface reads neither. Owned by 6.5. |

Two consequences follow, and both improve the analysis:

1. **Stage 6 is not blocked on a scope decision.** The first draft told the user
   that R46's cost clause and R47's summary clause could not be satisfied without
   a scope revision. They can be satisfied inside Stage 6, from data already
   persisted, by 6.5. The pending-decision entry has been withdrawn.
2. **The gap is smaller and sharper than the first draft claimed.** The
   interface is not missing a *source* for either figure; it is failing to
   surface two sources that exist. That is a presentation defect, and it sits
   squarely inside the requirement rather than outside it.

The one item that remains a deliberate exclusion, and is **not** a gap, is
in-application code and diff inspection: R47 places that in external IDE tools,
which is the accepted product direction, and the interface states where to look.

**A note on method, because it is the part worth keeping:** P07 and R46 both
require that an unobserved quantity render as explicitly unavailable rather than
as zero. That rule is about the *view*. It says nothing about whether the
*capability* exists, and it must not be used to excuse a missing capability —
that is precisely the substitution this section originally made, and it would
have quietly converted an implementation gap into an accepted limitation.

## 9. What 6.1 completion does not mean

- **No interface code was written.** 6.1 produced documents only. `internal/tui`
  is unchanged from `27182de`.
- **No requirement was met.** The amendments made R11/R45/R46/R47/R70
  measurable; they did not make the interface satisfy them.
- **Stage 6 is not complete.** Eight implementation sub-stages remain.
- **No human has seen any of this.** The captures are from a disposable fixture
  driven by an agent. Nothing here is evidence that the interface is usable,
  and none of the human-gated operations were touched.
- **The inventory was measured on Linux.** A native macOS re-measure was
  attempted and is blocked on SSH authentication, not on reachability; see
  [the results document](../../research/stage-6/results.md#6-validation). No
  macOS-specific interface behaviour is claimed. Stage 6.2 must re-measure on
  macOS before any of its sub-stages claim interface completeness.
