## Outcome and dependencies

Give the interface the end of the product. Twenty product commands have no
interface surface: exact-tree commit, plan-ref push, draft hosting request,
delivery status/cancel/reconcile/attested-close, factual archive
build/show/export/narrative, finalization run/quarantine, and retention
inspect/expire. None of them is mentioned anywhere in the interface.

6.7 adds reach for eighteen register entries. It adds **no new product
capability** and **no delivery authority**: every action it offers is the
existing command, behind the existing per-operation human grant, with the
existing refusal guards untouched. Production dispatch stays disabled.

## Invariants 6.7 must not break

These are the accepted delivery safeguards. A change here is a candidate
failure, not a UI convenience.

1. **Three separate approvals.** Commit, push and draft each prepare their own
   distinct inbox request and each consume their own exact grant. The interface
   must not let one approval authorize two operations, or reuse a grant across
   operations.
2. A commit advances **only** the approved non-checked-out plan ref, by
   compare-and-swap. It never changes the user's index, worktree or HEAD. The
   screen must show the ref, the parent and the tree before approval.
3. A push is exactly `HEAD_OID:PLAN_REF`, never force, never with tags, never
   with extra refspecs. The screen must show the destination ref, the approved
   predecessor and the old and new object IDs **before** approval.
4. A draft request is created by a single POST and only after bounded exact
   head/base search. A timeout or ambiguity is uncertain; a retry without a
   grant observes only. The screen must never offer a second POST.
5. `delivery-cancel` closes only a prepared, never-started operation.
   `delivery-reconcile` never records that an unobserved effect did *not*
   occur, and re-attempts a push only. `delivery-close-unobserved` is
   human-attested, final, and the attestation text is stored and shown back.
6. A delivery that started but never journaled is never attempted; the screen
   must point at `push-execute`/`commit-execute`/`draft-execute` instead.
7. A committed closure is never reopened.
8. Recommit/reconcile of the same command ID returns its receipt, never a
   second effect.
9. Production delivery stays disabled. Fixture hosting is credential-free
   loopback and stays labelled.
10. The acceptance of a plan creates no commit, push, publication or delivery
    authority. 6.5's review screen and 6.7's delivery screens must not blur.
11. There is no merge command and no merge endpoint. The interface says so.
12. `archive-export` never overwrites, and the destination's named parent must
    be a real directory, not a symbolic link.
13. Finalization is limited to accepted disposable fixtures with a `fixture_core`
    acceptance, and needs explicit `--live-local` authorization.

## Work checkpoints

### A. Delivery operation list and status

- [ ] Per plan, every delivery operation with its kind, state, the grant it
      consumed, the delivery journal row, and the phase.
- [ ] `delivery-status` as a screen that renders the **approved comparison
      operands** — target ref, approved predecessor, approved tree/head, or
      project/head/base — next to the fresh observation. This is what lets an
      operator resolve a diverged observation without re-deriving the intent,
      and it is the difference between a usable and an unusable delivery screen.
- [ ] Render `observed`, `uncertain`, `reconciled`, `executing`, `prepared` and
      a committed closure marker as visibly different states, with the reason
      when there is one.

### B. Commit

- [ ] `commit-prepare`: enter the plan, repository, task, exact repository-
      relative paths and message; the screen shows the **previewed tree, its
      parent, the plan ref, the paths and the acceptance identity** before the
      approval request exists. Reject paths outside the accepted task scope,
      nested repositories, `.git` and `.vigil` visibly, with the reason.
- [ ] `commit-execute`: the grant is selected from this operation's own
      approval, consumed once, with the resulting commit OID and journal row
      shown. The screen states that it does not touch the index, worktree or
      HEAD.
- [ ] Reconcile path: re-running without a grant reconciles an already-started
      operation and never commits twice.

### C. Push

- [ ] `push-prepare`: show the enrolled remote's single fetch/push URL, the
      exact local plan ref and head commit, the exact remote destination ref,
      and the approved predecessor. For an SSH remote, the `credential_ref`
      selection is a closed set and the screen shows that the credential is a
      **name**, never a value.
- [ ] `push-execute`: push, then the observed remote ref. A lost or ambiguous
      response renders as uncertain with the rerun-without-grant instruction.

### D. Draft request

- [ ] `draft-prepare`: provider (`github`/`gitlab`), project, `api_base`, base
      branch, title, body and `credential_ref`; the screen shows the required
      succeeded exact-head push, the current plan acceptance, the factual
      archive, and the **observed destination base OID** it will bind.
- [ ] `draft-execute`: the created draft URL, appended to a new factual archive
      revision, shown with the archive revision it landed in.
- [ ] A hosting response that created the request as non-draft renders as an
      uncertain external side effect requiring manual remediation — with that
      wording, not as a success.
- [ ] A permanent statement on the delivery screen that **no merge endpoint
      exists**, because R41 excludes automatic merging and a user must not infer
      otherwise from the interface's silence.

### E. Cancel, reconcile, attested close

- [ ] `delivery-cancel`: available only on a prepared, never-started operation,
      with the guarantee stated ("no grant consumed, no delivery journal row").
- [ ] `delivery-reconcile`: state the rule before it runs — automatic closure
      requires positive proof the approved effect happened; a push whose
      destination still holds the approved predecessor re-attempts the identical
      non-force push; nothing else is retried; a plan or remote ref moved by a
      third party is left open because absence is not proof of non-delivery.
- [ ] `delivery-close-unobserved`: an explicit human attestation. The screen
      requires the attestation text, shows it as final, and `delivery-status`
      displays it back so a later reader can distinguish "the system proved
      this" from "a person asserted this".
- [ ] All three confirmed through 6.2's confirmation step with the displayed
      revision and the exact operation ID.

### F. Archive

- [ ] `archive-build`: show the preconditions that were rechecked — current
      independently accepted plan and task set, unchanged accepted repository
      fingerprints, available durable evidence — then build. Show the new
      archive revision and the **visible system finalization task** it created.
- [ ] `archive-show`: the manifest with **every referenced durable artifact
      re-verified**, and any verification failure shown rather than hidden.
- [ ] `archive-export`: the destination's named parent checked and stated as a
      real directory, a refusal to overwrite shown before the attempt, and the
      written portable references and separately typed external URLs shown
      afterwards. State that export is a copy, not a commit and not a
      publication.
- [ ] Show the per-plan view materialised in the Git-ignored `.vigil` folder and
      the `.git/info/exclude` entry, including a `view_warning` when the view
      could not be written — reported as a warning on a committed archive, not
      as a command failure.
- [ ] `archive-narrative`: the citation set is **selected from the validated
      manifest's own reference set**, never typed, so a citation outside the
      manifest cannot be submitted.

### G. Finalization and retention

- [ ] `finalization-run`: the selected profile, the six route identity fields
      the runner will compare, the reserved allowance from the shared plan
      services ledger, the archive revision and manifest digest, and the
      explicit local-route authorization. Show that the run is limited to
      accepted disposable fixtures.
- [ ] A failed idle-observed result renders as `finalization_pending` with the
      charged elapsed time, and the retry action is a **narrative-only** retry.
      State that accepted development is not rerun.
- [ ] `finalization-quarantine`: show what it does conservatively — the run
      becomes `unknown` with `unconfirmed` writer state, the global fence stays
      held, the full reserved cap is charged as unknown, the task returns to
      `ready` — and that it never asserts a native writer stopped.
- [ ] `retention-inspect`: the exact dry-run candidate set as a durable human
      receipt, listing each candidate and each reason it is eligible.
- [ ] `retention-expire`: bound to that exact visible receipt and the displayed
      revision; a changed candidate set or a missing or consumed receipt refuses.
      Show what expiry marks unavailable before deleting, and state that it does
      not touch durable evidence, checkpoint artifacts or global harness
      history.

### H. Live routes, for completeness

- [ ] `planning-run` and `planning-reconcile` become reachable, with the
      prepared manifest and optional private key entered as paths — never
      credential values — and the proposal-application refusal while an attempt
      remains unresolved shown on screen.
- [ ] `tool-qualify` becomes reachable as a qualification action, distinct from
      any day-to-day action, and its "grants no execution, acceptance, spending,
      delivery or publishing authority" statement is visible.
- [ ] `tool-server` stays excluded; the exclusion register must say so where an
      operator might look for it.

## Autonomy and user gates

Autonomous: everything, against a local bare remote and a fake hosting server.
That is exactly how Stage 5.6 and 5.7 qualified these commands, and
`make scenario` already exercises them.

User gates: a real GitHub or GitLab host, a real remote, a real credential
reference, a real credentialed model route for finalization and planning, and
native macOS evidence. All are **Stage 8's** or blocked. 6.7 records the exact
missing step and does not claim real delivery.
