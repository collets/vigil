# Stage 6.9 — Parity closure, exclusions and the Stage 6 feature list

<!-- vigil-tier: plan -->

Status: **planned; not started.** Written 2026-09-30 by
[Stage 6.1](6.1-parity-gap-analysis.md). Depends on 6.2 through 6.8.

## Outcome and dependencies

Close [Stage 6](stage-6.md) against its own four stated outcomes, and finish
the deliverable Stage 7 documents from and Stage 8 tests against:
[`research/stage-6/results.md`](../../research/stage-6/results.md) with a
**complete** feature list of the terminal interface — every screen, every
action, every key binding, the command each action maps to, and its requirement
coverage.

6.9 implements almost no interface code. Its work is audit, closure and
evidence. It is the last sub-stage because the feature list is accumulated by
6.2–6.8 and can only be audited once they have landed.

## Work checkpoints

### A. Parity audit

- [ ] Walk the real Cobra tree and the real `Engine.Apply` kind list against the
      machine-readable parity table. Every entry must be classified, and the
      table's own check must be green. An entry still marked `planned` after its
      owning sub-stage landed is a closure failure, not a documentation note.
- [ ] For every `C` row, confirm the interface really performs the capability
      **and** that the documented compromise is the one actually in force. A `C`
      row that has quietly become `E` — or has become something else — is
      updated in the same change.
- [ ] For every `X` row, confirm the reason still holds. An `X` whose reason was
      a Stage 6 scope decision is stated as a scope exclusion, not as a
      technical impossibility; the two must never be blurred, because only one
      of them would justify revisiting the scope.
- [ ] Confirm the two **product gaps** are still recorded as gaps and were not
      papered over: no cost or usage figure anywhere, and no persisted
      implementation summary. If a sub-stage invented either, that is a
      **blocking finding**, because Stage 6 must not add product capability.
- [ ] Confirm the closed production gates are still closed and still rendered as
      closed. A Stage 6 sub-stage that enabled any of them is a blocking
      finding.

### B. The complete feature list

- [ ] Every row in §5 has a filled `Screen`, `Keys` and `Command` column, or an
      explicit reason it is not applicable. No row may remain `planned`.
- [ ] Every action listed maps to exactly one command or envelope kind, and
      every command in the register is driven by at least one listed action or
      is classified `X`. A test should assert both directions of that mapping.
- [ ] Every row carries its requirement coverage, and every amended requirement
      (R11, R45, R46, R47, R70) and every new condition (P13–P18) has at least
      one row or is covered by the P-condition's own acceptance test.
- [ ] The key-binding column is the **authoritative** binding list, replacing the
      CLI reference's dashboard key table where the two differ. If the
      interface has diverged from
      [`stage-5-cli.md`](../stage-5/stage-5-cli.md)'s `Terminal dashboard` table,
      the CLI reference is corrected in the same change — the interface is the
      product, and the CLI reference must describe it accurately.
- [ ] Re-measure the whole interface from the built binary at 110, 80, 60 and 40
      columns and replace §2's captures with the final state. The measured
      inventory must describe the delivered interface, not 6.1's starting point.

### C. Requirement verification

- [ ] **P13** — every leaf command and envelope kind is classified, verified by
      the 6.2 parity test and re-run here.
- [ ] **P14** — every human decision class has a distinct action bound to the
      displayed exact revision, verified by 6.4's per-class test and re-run here.
- [ ] **P15** — the cold-start main-screen assertion, verified by 6.3 and
      re-run here.
- [ ] **P16** — navigation from a visible focus, and explicitly unavailable for
      unobserved quantities, verified by 6.5 and re-run here.
- [ ] **P17** — the human review screen's contents, verified by 6.5 and re-run
      here.
- [ ] **P18** — no repository process serves a browser or network UI, and the
      completeness claim is backed by this feature list. The first half is a
      test over the dependency manifest and the command tree; the second half is
      this document.
- [ ] Re-audit R11, R45, R46, R47 and R70 **as amended** and record, per
      requirement, whether it is now met, and on what evidence. If a requirement
      is still not met, 6.9 says so plainly and Stage 6 does **not** close. A
      partial result is a valid outcome; a favourable summary over a partial
      result is not.

### D. Stage 7 and Stage 8 handoff

- [ ] Write 7.1's inputs: the screens, actions and concepts Stage 7's site must
      document, drawn from the completed feature list, and anything in the
      feature list a user cannot reasonably self-serve from the interface.
- [ ] Write 8.1's inputs: the human-gated steps the feature list shows are now
      reachable — real human acceptance, `Cannot verify`, real commit, real
      push, real draft request, real resource attestation, real retention
      expiry, real finalization — each with the interface path an operator would
      take. This is what turns "deferred to Stage 8" from a note into a
      walkthrough.
- [ ] Record the exact validation evidence for each, so Stage 8 can distinguish
      "the interface offers it" from "a human has done it". Only the second is
      Stage 8's to establish.

### E. Documentation and status

- [ ] `docs/STATUS`, every `status_documents` entry's canonical marker and
      prose, [`next-steps.md`](../../process/next-steps.md)'s status line and
      "Next concrete action", and [`docs/README.md`](../../README.md)'s index
      are updated in one change, exactly as the repository's stage-status
      discipline requires. `make docs-check` is part of the definition of done.
- [ ] This document's own status line flips, and the results document's
      "skeleton" status is replaced with its completed state.

## Validation and completion criteria

| Check | Command |
| --- | --- |
| Vet and full suite | `make check` |
| Documentation gate | `make docs-check` |
| Race | `make check-race` |
| Builds and cross-builds | `make build`, `make build-boundary`, `make cross-build` |
| Whitespace | `git diff --check` |
| Parity and acceptance | every P13–P18 acceptance test, re-run at the candidate SHA |
| Full regression | `make scenario`, with the report read back |
| Boundary probes | `make scenario-guard-check` |
| Interface capture | 110/80/60/40 columns against a fresh fixture, natively on **both** Linux and macOS |

Completion requires all of:

- [ ] All gates above pass at the candidate SHA.
- [ ] Native macOS interface evidence exists for the delivered interface. If
      access is still blocked, Stage 6 records the blocker as an open user gate
      and does **not** claim the interface was validated on the second
      supported platform. This is not a formality: 6.1 recorded that Linux
      evidence alone missed a portability defect in Stage 5.7.
- [ ] The parity table has no `planned` row and no unclassified entry.
- [ ] The feature list has no `planned` row, and every key binding in it was
      read back from the built binary.
- [ ] R11, R45, R46, R47 and R70 are each recorded as met or not met, with the
      evidence. Stage 6 closes only if all five are met.
- [ ] No production gate was enabled, and no product capability was added.
- [ ] An independent adversarial review accepted the exact candidate SHA, and
      the verdict is recorded in
      [`docs/research/stage-6/`](../../research/stage-6/).

## What Stage 6 completion is not

Restated from [the scope document](stage-6.md) and **not** weakened here:

- It does **not** mean the product works for a real user. No human has used the
  delivered interface.
- It does **not** mean any delivery path works. Nothing has been run against a
  credentialed model or a real remote; production dispatch remains disabled.
- It does **not** claim the
  [milestone](../../core/mvp-acceptance.md) is demonstrated. That is Stage 8's.
- It does **not** reopen Stage 5. No Stage 5 finding is re-litigated here; a
  Stage 6 change that breaks an accepted safeguard is a new blocking finding in
  the Stage 6 slice, remediated on the Stage 6 branch.

## Handoff

Stage 6 complete means: the feature list is authoritative and complete, the
parity register has no unclassified or planned row, R11/R45/R46/R47/R70 are
recorded as met with evidence, and the next stage is [Stage 7](../stage-7/stage-7.md)
with its inputs written by checkpoint D. Record the candidate SHA, every
validation result, the native macOS result or the open gate, and any open
finding, in [`research/stage-6/results.md`](../../research/stage-6/results.md).
