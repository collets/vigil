# Stage 6.2 — Interface architecture, key safety and the parity register

<!-- vigil-tier: plan -->

Status: **planned; not started.** Written 2026-09-30 by
[Stage 6.1](6.1-parity-gap-analysis.md) from the measured gap at `27182de`.
This is the first implementation sub-stage of [Stage 6](stage-6.md).

## Outcome and dependencies

Replace the single-`View()` interface with a screen-stack architecture that has a
real focus model, scopes keys to the focused screen, makes every binding
discoverable at any terminal width, and installs the **mechanical parity
register** that fails when a product command is not classified.

6.2 is first because every later sub-stage navigates through the model it
establishes, and is checked by the parity test it installs. 6.2 deliberately
changes **no product surface**: it moves the interface's structure, not its
reach. The 4 fully expressed and 9 partially expressed capabilities stay
exactly as they are at the end of 6.2 — that is the regression boundary.

Depends on [6.1](6.1-parity-gap-analysis.md) only. No dependency on Stage 5.1's
live Codex route, on live inference, or on any hosted remote.

## Invariants 6.2 must not break

These are the accepted Stage 5 safeguards. 6.2 is a refactor of presentation
plus a new check, so any change here is a defect:

1. Every action stays bound to the **visibly displayed** exact revision,
   request ID, run ID, task ID or proposal revision. Stale revisions keep
   failing closed.
2. `clean()` keeps stripping ANSI and control characters from every persisted
   string, including the new screens' fields. Untrusted harness text stays
   untrusted text.
3. The bounded clarification input keeps its 4096-byte cap, its empty-answer
   refusal and its "Esc abandons local input" semantics.
4. Mutations stay asynchronous: input must never block behind a pending read or
   a pending mutation, and `q` must still work during both.
5. A failed refresh keeps the previous snapshot and shows a visible warning.
6. No key may start a model, reconstruct a provider request handle from
   persisted or rendered text, or create delivery authority.
7. The view never exceeds terminal width or height, and never renders a raw
   control sequence.
8. `--synthetic-interactions` remains the only way to reach owner-routed
   mechanics, and it remains refused for production runs.

## Work checkpoints

### A. The screen model

- [ ] Introduce a screen interface with `Title`, `Focus`, `Lines`, key
      dispatch and an explicit "does this screen mutate persisted state" flag.
- [ ] Implement a screen **stack**: push, pop and replace, with `esc` popping
      one level and quit as a distinct explicit action. Losing a screen must
      never lose entered-but-unsubmitted text silently; pop with a pending
      form asks first.
- [ ] Give every screen exactly one focus that is rendered on every frame, so
      "what will this key act on" is always answerable from the display.
- [ ] Split `internal/tui` into one file per screen plus a shared shell
      (`model.go`, `shell.go`, `screen.go`, and one file per screen). Close
      6.1-F14 and 6.1-F21. No file in `internal/tui` should exceed roughly 400
      lines; `go vet` and `make check` must stay clean.
- [ ] Move every one of the twenty action strings and its bindings unchanged.
      Add a test that asserts the exact set of twenty action strings is
      unchanged by this sub-stage, so a refactor cannot quietly drop one.

### B. Key scoping and safety — closing 6.1-F17, 6.1-F18, 6.1-F16

- [ ] Scope every mutating key to the screen that owns it. Project-level
      controls (`pause`, `continue`, `advance`, `queue`, `stop`) must not fire
      from History, Detail or any new screen without that screen registering
      them. Close 6.1-F17; the regression test presses each control from a
      screen that does not own it and asserts no persisted change.
- [ ] Require an explicit confirmation step for the actions that consume
      authority or can lose progress: stop, checkpoint clear, checkpoint
      restore, delivery cancel, delivery reconcile, retention expire. The
      confirmation shows the exact displayed revision and the exact target ID.
- [ ] Make `esc` pop one level; require an explicit quit action, with a
      confirmation when a run is active or a form holds unsaved text. Close
      6.1-F18.
- [ ] Replace the single truncated footer with a per-screen binding line **plus**
      an in-application help screen listing the full binding set for the
      focused screen, its parent screens, and the global keys. The binding line
      must degrade to a count plus a pointer to help rather than truncating
      mid-list. Close 6.1-F16; assert at 40, 60, 80, 110 and 200 columns that no
      binding string is cut and the tab/screen bar stays readable.
- [ ] Add a bounded text-entry component with a visible length counter,
      character-set policy and a non-empty guard, and use it for the existing
      clarification path. Preserve the 4096-byte cap exactly.

### C. Project selection

- [ ] When more than one project is registered, the shell selects one at start
      and offers switching, so the interface is not hard-wired to a single
      project argument. Keep `vigil dashboard PROJECT_ID` working unchanged.

### D. The parity register and its check — the anti-silent-gap mechanism

- [ ] **First, make the envelope-kind list walkable.** The 14 `apply` kinds
      exist only as `case` labels inside the `switch` in `Engine.Apply`
      (`internal/core/core.go`), plus `repository.enroll`, which is an early
      `if` *before* the switch. There is no exported list, so a test that
      "walks the real kind list" would have to hardcode the 14 strings and would
      then be checking the parity table against a copy — exactly the drift the
      check exists to prevent. Introduce an exported `core.EnvelopeKinds`
      derived from the switch, and make `Apply`'s `default` branch reject
      anything not in it, so the list cannot drift from the implementation. A
      `ValidateEnvelopeKind` predicate is **not** an acceptable substitute: the
      test has to *walk a list*, and a predicate would leave the 14 names
      hardcoded in the test, which is the very thing being eliminated. This is
      the one place 6.2 touches `internal/core`, and it is a pure refactor: no
      behaviour changes.
- [ ] Move the classification data from
      [`results.md`](../../research/stage-6/results.md#4-parity-register) into a
      machine-readable form in the repository — a Go table in `internal/tui`
      (or a package the interface and the check both import) is preferred over
      a data file, so it is type-checked and cannot drift from the code.
- [ ] Every entry records: the command or envelope kind path, its
      classification (`E`, `C`, `X`), the owning sub-stage, and — for `C` and
      `X` — the reason or compromise text. The reason text must be the same
      text as the register's, so the document is generated from or checked
      against the table.
- [ ] Add a test that walks the **real Cobra tree** via `cli.NewCommand()` and
      the **real `core.EnvelopeKinds`**, and fails when any entry is missing,
      duplicated or unclassified. This is the check that stops the interface and
      the product from diverging again, and it is the deliverable 6.1's scope
      document asked for.
- [ ] Add a test that asserts each `X` entry appears in the **closed exclusion
      list in `docs/core/requirements.md`**, and that no capability absent from
      that list may be classified `X`.
- [ ] **Be precise about what that test does and does not achieve**, because an
      earlier draft of this plan claimed more than it could deliver. The test
      catches *drift* between the register and the list: an `X` that nobody
      sanctioned, or a sanctioned entry nobody classified. It does **not**
      prevent an agent from adding an entry to `requirements.md` and classifying
      the matching row `X` in the same commit — that satisfies both clauses and
      the test passes. Unlike the installed migrations, `requirements.md` is a
      live core document, so no mechanical gate can make it immutable here
      without a change of the repository's own rules, which is outside Stage 6's
      authority. **The guarantee is therefore procedural and review-enforced:**
      adding an entry is a user scope decision, the entry lives in the
      requirements baseline rather than in a Stage 6 deliverable, the two copies
      are pinned against each other, and every change to either copy is visible
      in an independent review's diff. Say this in the test's comment as well as
      here, so nobody later reads the green test as more than it is.
- [ ] Add a test that asserts the **canonical exclusion list and its mirror in
      `docs/research/stage-6/results.md` §5.9 are identical** — same entries, same
      reason class, same reason text — so the two copies cannot drift. The
      baseline is canonical; the mirror is a copy.
- [ ] Add a second test that fails when an entry marked `planned` for a
      sub-stage that has landed is still `planned` in the machine-readable
      form. The table, not the prose, is the source of truth.
- [ ] Keep `make docs-check`'s CLI-reference check green. If a command is
      added, removed or renamed, the parity table and
      [`stage-5-cli.md`](../stage-5/stage-5-cli.md) must both change in the same
      commit.

## Autonomy and user gates

Autonomous: everything above. 6.2 needs no model route, no credential, no
network, no hosted remote and no human decision.

User gates, none of which 6.2 may assume:

- **macOS SSH access** for the native capture. Blocked at 6.1 on
  authentication; the exact attempts are recorded in
  [`results.md`](../../research/stage-6/results.md#native-macos-attempted-and-blocked).
- Nothing else. 6.2 changes no product capability, so it creates no delivery,
  spending or dispatch authority.
