## Outcome and dependencies

Give the inbox every decision the product asks a human to make, as a distinct
revision-bound action, with no decision reachable only by leaving the
interface. Today 6 of the 25 human decision classes are fully expressed, 6 are
partial and 13 are absent. Of the 19 that are not fully expressed, 6.4 owns
**six** — classes 1, 2, 3, 9, 10 and 12, the ones resolvable inside the inbox —
6.5 owns three (13, 14, 16), 6.6 owns one (22), 6.7 owns seven (17–20, 23–25)
and 6.8 owns two (4, 21).

6.4 adds the missing decisions and closes defects 6.1-F3, F4, F5, F6, F9 and
F19. The register assigns it **nine rows**: `inbox`, `proposal-apply`,
`proposal-decide`, `execution-recovery-choose`, `planning.proposal.apply`,
`planning.proposal.decide`, `operation.request`, `permission.grant` and
`permission.revoke`. It adds no new product capability: every action it offers
already exists as a CLI command or an `apply` envelope kind.

Depends on 6.2's screen stack, scoped keys, bounded text entry and
confirmations. Needs 6.3's triage so the request list is reachable from the
main screen.

## Invariants 6.4 must not break

1. Every decision stays bound to the **visibly displayed** exact request and
   the exact displayed project revision. A stale display must still fail.
2. A decision the request's own type does not support must still fail with a
   distinct message; the interface must not route one request type through
   another request type's command.
3. `y` must never widen a grant beyond what the operator selected. A grant with
   no expiry selected must record no expiry, not a default one.
4. Native clarification delivery remains owner-routed, remains persisted before
   delivery, and an unproven delivery remains uncertain and is never replayed.
5. A human decision is never simulated. Fixture-labelled paths stay labelled.
6. The bounded 4096-byte answer cap and the non-empty guard are unchanged.
7. A confirmation step is required for any decision that consumes authority or
   can lose progress, and it must show the exact displayed revision and target.

## Work checkpoints

### A. Request triage — closing 6.1-F3 and 6.1-F19

- [ ] Render request **age** from the already-selected `InboxEntry.CreatedAt`
      and the already-selected `InboxEntry.Blocking` flag. Both are in the
      snapshot today and are discarded.
- [ ] Add a kind filter and a state filter, and show the count of hidden items
      when a filter is active, so filtering never silently hides a blocking
      request.
- [ ] Render an expired request distinctly from a pending one; the snapshot
      already computes `expired` in the state field.
- [ ] Suppress empty identity fields instead of printing `Plan  · Task  r0 ·
      Run`. Close 6.1-F19.
- [ ] Sort so blocking requests precede non-blocking ones, and so a request
      past its deadline precedes an ordinary pending request. Show the ordering
      rule on screen so it is not a surprise.

### B. Permission decisions — closing 6.1-F9

- [ ] `allow` must offer all four documented scopes — `once`, `task`, `plan`,
      `project_permanent` — and the operator must select one explicitly. No
      scope may be the silent default.
- [ ] Offer an explicit optional expiry in Unix milliseconds, validated exactly
      as `permission.grant` validates it, with **no** default: absent means
      absent in the persisted command.
- [ ] Surface the request's `resource_digest`, `arguments_digest`,
      `policy_epoch` and the decision scope (`once`) in the detail view, so the
      operator can see what they are authorizing. These are already in the
      snapshot; render them.
- [ ] Add a **grant list** screen per request and per project, showing grant ID,
      scope, origin, creation and revocation. `InboxEntry.GrantID`,
      `GrantScope` and `GrantOrigin` are already selected for a pending request
      and shown only there.
- [ ] Add `permission.revoke` as its own action, bound to a selected grant ID.
      This is the first time any interface can reach it.
- [ ] Show project, plan and task restrictions and their origins next to a
      request, so a request that is permanently refused by policy is visibly
      refused rather than mysteriously denied. This needs the read model 6.5
      also needs; add it in `internal/core` here and share it.
- [ ] Add `operation.request` as a reachable action from a visible intent, so
      the request/grant cycle can be started from the interface rather than
      only by a `commit-prepare`-style prepare command.

### C. Proposal decisions — closing 6.1-F5 and 6.1-F6

- [ ] Add an **explicit authorization control for acceptance-criteria changes**
      to the proposal-apply flow, so `authorize_criteria_changes` is the
      operator's choice rather than a hardcoded `false`. It must default to
      *not authorized*, require a deliberate act to enable, and appear in the
      confirmation. This is R23's "prohibit autonomous acceptance-criteria
      changes" made operable rather than merely absent.
- [ ] Replace the two hardcoded rationale strings with a bounded operator
      rationale for both `reject` and `request_revision`. Keep a non-empty
      guard; do not invent a default reason, because the stored rationale is
      the record of why a human refused a proposal.
- [ ] Show the proposal's full definition — objective, criteria, dependencies,
      scope, checks, limits — in the request detail before the apply, reject or
      revise decision, not only its ID, revision, digest and author. A decision
      about a definition the interface does not show is not a human review.

### D. Recovery decisions

- [ ] Add the explicit history-observation form: history state (`readable`,
      `missing`, `corrupt`, `unsupported`), recovery class, and the
      automatic-work flag. These are the `--history-state`, `--history-class`
      and `--history-automatic-work` inputs, and they are substantive: the
      automatic-work flag **disqualifies** exact resume, so it is a refusal
      input and must be presented as one.
- [ ] The form must display the consequence of the selected combination before
      the choice is accepted, including that exact resume is refused under
      automatic work and that `fresh_context` requires a verified checkpoint.
- [ ] Show the destination checkpoint that a restore or fresh-context choice
      would bind to.
- [ ] Keep `x`, `f` and `b` and `remain-blocked` exactly as they behave today;
      it is the only fully correct decision group in the interface.

### E. Input and clarification

- [ ] Leave the existing answer/dismiss/cancel mechanics intact; add the
      request's age, kind and the exact bound that was applied.
- [ ] For a native clarification, show that delivery is owner-routed and that
      the answer will be persisted before delivery, and show the resulting
      `delivered` / `proven_not_delivered` / `unknown` state afterwards. The
      dashboard already receives the inspection result; surface it.

## Autonomy and user gates

Autonomous: all of it, for the fixture and offline paths. The decision classes
themselves are exercised against labelled disposable fixtures, exactly as the
CLI's own quality path is, and the labels stay visible.

User gates: the real human decisions — a real human accepting a real task, a
real commit, a real push, a real draft request, a real resource attestation —
are **Stage 8's**. 6.4 makes them reachable; it does not perform them. Native
macOS evidence remains open on authentication.
