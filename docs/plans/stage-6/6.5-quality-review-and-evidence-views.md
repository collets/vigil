## Outcome and dependencies

Build the screen R47 has never had: a human review view that shows what is
actually being accepted, and make the quality surface real instead of
counted. Today reviewer findings are two integers, check results are three
colon-separated fields, three of four human decisions are unreachable, three of
four manual outcomes are unreachable, and plan-wide acceptance does not exist in
the interface.

The register assigns 6.5 **eight rows**: `reservation`, `artifact`, `artifacts`,
`quality-check`, `quality-review`, `quality-manual`, `quality-decision` and
`quality-accept`, plus the usage/cost and change-record surface that R46 and R47
require and that this slice surfaces from already-persisted data. 6.4 builds the
effective-restrictions read model that 6.5 reuses. 6.5 adds no new product
capability: every command it exposes already exists, and every figure it renders
comes from data the application already persists. An earlier 6.1 draft believed
the cost/usage and implementation-summary capabilities were missing and filed
them as product gaps; that was false, and the correction is at
[6.1 §6](6.1-parity-gap-analysis.md#6-correcting-two-claims-this-analysis-originally-got-wrong).

## Work checkpoints

### A. Read models for quality evidence — closing 6.1-F11, F12, F4

- [ ] Add read models for **individual findings**: id, severity, blocking flag,
      resolution, text, and location, scoped to the exact task or plan. They are
      persisted and unread today.
- [ ] Add read models for **individual check results**: check ID, status, exit
      state, duration, output artifact reference, and the resolved evidence
      reference. The current roll-up concatenates three fields into a string and
      drops the rest.
- [ ] Add read models for **individual manual outcomes** with their criterion,
      state, notes, evaluator and evidence reference.
- [ ] Add read models for **baseline exceptions** with the specific accepted
      failures, so an unhealthy project is explained rather than reported as a
      boolean.
- [ ] Add read models for **budget ledgers**: remaining, charged, unknown, and
      the excluded approval and resource wait segments, per task and per plan
      services. R61 requires the exclusion to be visible, not just the total.
- [ ] Reuse the **effective-restrictions read model that 6.4 builds**, rather
      than adding a second one. 6.4 owns it because a request detail must show
      *why* an allow would be permanently refused by policy; 6.5 consumes it on
      the review screen. One owner, one read model.
- [ ] All read models must come from **one** consistent snapshot per screen, as
      `Dashboard` does today. A screen that mixes two revisions is the defect
      class 6.3's checkpoint A warns about.

### B. The human review screen — closing 6.1-F13

- [ ] One screen, per task and per plan, that shows everything the acceptance
      command will recheck: the task definition, its criteria, the current
      fingerprints, every check result, every finding, every manual outcome, the
      effective restrictions, the budget position, and the artifacts.
- [ ] The four decisions are **distinct actions on that screen**, each visibly
      bound to the displayed revision, each with a typed rationale:
      `accept`, `request_changes`, `clarify`, `stop`. Close 6.1-F7; the current
      hardcoded `accept` and hardcoded rationale go away.
- [ ] Task acceptance and plan-wide acceptance are **distinct actions** bound to
      their own displayed scope. Close 6.1-F10. A plan's acceptance must show
      that it re-observes every child task's acceptance.
- [ ] The screen must state that acceptance creates no commit, push,
      publication or delivery authority. R24's acceptance and R28's delivery are
      different products; the interface must not let the operator infer
      otherwise.

### C. Quality actions

- [ ] Run a declared check: select from the task's or plan's **declared**
      required set, show the definition's argv, cwd, environment, required
      outputs and timeout before running, and show the live state, then the
      result. Never offer a check the definition set does not contain.
- [ ] Record a fresh review: the closed schema is entered through a guided form
      with the required **fresh, distinct** session ID and native identity shown
      as two separate fields, because reusing an implementation identity is the
      failure this command exists to prevent.
- [ ] Manual outcomes: all four of `pass`, `fail`, `cannot_verify`, `pending`,
      each with notes and evaluator, each on the criterion the operator selected
      and each visibly bound to the displayed revision. Close 6.1-F8. R52's
      `Cannot verify` is a real human decision and must be as available as
      `pass`.
- [ ] Manual prerequisites with their satisfied state and evidence, and the
      blocked task they cause when unsatisfied.
- [ ] Show the unobserved-quantity rule in the interface itself: any figure the
      application does not observe renders as explicitly unavailable, with the
      reason. P16 and P07.

### D. Artifacts and evidence

- [ ] Artifact list with kind, digest, size, referencing scope, and the
      orphan/corruption report, without deleting anything. R25.
- [ ] A bounded evidence viewer for a check output and a review result, opened
      from the finding or check that cites it. Every byte sanitized through
      `clean()` before rendering; the viewer is bounded in both size and lines
      and says when it truncates.
- [ ] The resource reservation journal view: owning instance, intended run, all
      participating roots, observed claim and ticket generations, and phase. It
      neither acquires nor releases anything, and the screen must say so.
- [ ] Publish an artifact, with the 16 MiB bound and the kind shown before the
      publish.

### E. Usage, cost, change records and the implementation summary

- [ ] Where cost and token usage would appear, render the values that
      `usage_observations` already holds — tokens, cost, currency and the
      `observed`/`estimated` provenance — per attempt and cumulatively. Where a
      run has **no** usage observation, render an explicit "unavailable" state
      with the reason. Do **not** render zero, and do **not** omit the row
      silently. P07 governs this and the data is already there.
- [ ] Where the implementation summary for the current attempt appears, render
      `execution_results_v11.summary` for that run, together with its
      `status`, `changed_paths_json` and `repository_fingerprints_json`. Do not
      synthesise a summary from event kinds and present it as one: the real
      summary is persisted and must be read, not reconstructed.
- [ ] Both must be visible on the human review screen, not only in a detail
      view, because R47 asks for the summary *in human review* and R46 asks for
      the change record in a secondary view. A test must assert they render, and
      must assert that a run with no usage observation renders "unavailable"
      rather than `0`.

Completion requires all of:

- [ ] All gates above pass at the candidate SHA and `make scenario` reports no
      `unmet` row.
- [ ] **P17 is asserted by a test**: against a fixture with a recorded review
      carrying a blocking finding, a suggestion, two check results and a manual
      outcome, the human review screen's rendered content contains the
      blocking finding's severity, blocking status and text; the suggestion's
      distinct classification; each check's status, exit state and evidence
      reference; each manual outcome; and the statement of where to inspect code
      and diffs.
- [ ] **P16 is asserted by a test**: for a run with a usage observation, the
      tokens, cost, currency and `observed`/`estimated` provenance render from
      `usage_observations`; for a run without one, the screen renders an
      explicit "unavailable" state with a reason; and a test fails if either
      renders as `0`.
- [ ] 6.1-F4, F7, F8, F10, F11, F12 and F13 are closed with permanent tests.
- [ ] All four quality decisions and all four manual outcomes are reachable and
      each is a distinct action on a distinct key or selection, proven by a test
      that records the exact command each issues.
- [ ] Acceptance remains bound to the displayed revision and a stale display
      still fails closed, for both task and plan scope.
- [ ] Its 25 feature-list rows in [`results.md`](../../research/stage-6/results.md#5-feature-list)
      §5.5 — every row from `5.1` to `5.28` except the three already `done`

      usage/cost and the implementation summary — are read from their persisted

- [ ] An independent adversarial review accepted the exact candidate SHA.

## Autonomy and user gates

Autonomous: all checks, reviews, manual outcomes, decisions and acceptances
exercised against labelled disposable fixtures, which is how the CLI's own
quality path is qualified. Fixture labels stay visible; a fixture actor is
never real human acceptance.

User gates: a real human reviewing and accepting real work, and the real
`Cannot verify` decision, are **Stage 8's**. Native macOS evidence remains open
on authentication.
