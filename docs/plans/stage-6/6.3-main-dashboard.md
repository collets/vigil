# Stage 6.3 — Main dashboard, live run state and history

<!-- vigil-tier: plan -->

Status: **planned; not started.** Written 2026-09-30 by
[Stage 6.1](6.1-parity-gap-analysis.md) from the measured gap at `27182de`.
Depends on [6.2](6.2-interface-architecture-and-parity-register.md).

## Outcome and dependencies

Make the main screen the screen R45 says it must be: one view that, from a cold
start with no navigation, shows the active plan, the current task and its
blocker, the queue position, the live run and session state, the compact
per-task quality status and the actionable request list. Then turn History from
a wall of event labels into a navigable, filterable record.

This is the sub-stage that carries P15. It completes four register rows —
`status`, `events`, `queue` and `queue-list` — and adds **no new product
capability**; everything it shows and does already exists in the CLI.

Depends on 6.2's screen stack, focus model, scoped keys and help. No dependency
on any live route.

## Work checkpoints

### A. Read model for progression

- [ ] Add a `ProgressionDetail` read model in `internal/core` exposing, from
      **one** consistent snapshot like today's `Dashboard`: the active plan
      (id, revision, state, rank), the selected task (id, revision, state,
      blockers), the full ranked queue with the active plan's position, and
      whether execution is eligible with the exact blocking issues.
- [ ] Add the missing fields the interface is handed but never renders, so
      nothing depends on a hidden value: surface `ActiveRun` and `Queue` as
      first-class read-model fields rather than leaving them as
      implementation details of a mutator.
- [ ] Keep the single-snapshot guarantee. A screen that mixes a queue read from
      one revision with a task read from another is the exact class of defect
      the current `Dashboard` comment warns about; add a test that a concurrent
      writer cannot produce an inconsistent snapshot.

### B. Main dashboard

- [ ] Render, with no navigation required: active plan, current task and
      blocker, queue position, live run, compact per-task quality status, and
      the actionable request list with kind, **age** and **blocking** state.
- [ ] Compact quality status means, per task, a fixed-width roll-up: check
      results passed/total, blocking findings, suggestions, manual criteria
      outstanding, and baseline health. It must render a bounded, fixed-width
      summary, not a paragraph.
- [ ] Show an explicit "unavailable" marker for anything the application does
      not observe, never a zero. This is R46/P16 and P07 applied to the main
      screen; cost and token figures are the live case today (§5.9 of the
      results document).
- [ ] Make the actionable list's entries open the corresponding inbox request
      through 6.2's screen stack, so the main screen is a genuine entry point
      rather than a second inbox.
- [ ] Make `u` queue an explicitly named plan at an explicitly shown rank
      instead of the first queueable plan in the snapshot. **Regression test:**
      with two queueable plans, `u` on the first queues the first, and the
      queue line changes on screen.

### C. Live run and agent activity

- [ ] Add a read model for the active run: run ID, state, runtime kind, task
      and plan, generation, session identity, native request key, wall and
      active budget consumed, and the set of allowed next commands.
- [ ] Add a read model for **bounded, sanitized agent activity** derived from
      persisted events and session records: the recent event kinds with their
      sanitized labels, never raw harness output, never a reconstructed
      provider request handle. R45 as amended defines activity this way
      precisely so it cannot become a terminal scrape.
- [ ] Render it as its own screen reachable from the main dashboard's run line,
      not as a wall of text on the main screen. The main screen shows the run
      state and a one-line activity summary; the detail is one keystroke away.
- [ ] Render "no run is active" explicitly. A missing run is a state, not a
      blank line.

### D. History

- [ ] Add cursor and filter parameters to the events read model: `--after` is
      already available in the CLI and unused by the interface; add filtering
      by kind and a continuation cursor.
- [ ] Render an event list that is navigable and openable: sequence, time, kind,
      and — on open — the sanitized payload for the event kinds whose payload
      is safe and bounded to show. Enrich beyond `command_applied` where the
      payload is already closed and bounded; never render an unbounded or
      credential-bearing field.
- [ ] Show an explicit notice whenever the window truncates, with the cursor
      to continue from. Close 6.1-F20's silent truncation.
- [ ] Keep `q`, `esc` and every scoped key behaving as 6.2 defined; in
      particular History must not accept project control keys. That regression
      test is 6.2's and must still pass.
