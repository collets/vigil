## Outcome and dependencies

Let the interface **start** the product and define it, and make cross-instance
coordination visible. Today the primary interface cannot create a project
(6.1-F15), cannot configure policy, define a profile, import a specification,
define or reorder a plan or task, enroll or prepare a repository, register a
check, reach the `resources` tree at all, or run the boundary diagnostic.

The register assigns 6.8 **20 rows** — `doctor` (1), the three `resources`
commands (3), the ten definition/setup commands (`init`, `list`, `apply`,
`discover`, `repository`, `prepare-repository`, `spec-import`, `spec-show`,
`proposal-create`, `proposal-show`) and the six definition envelope kinds
(`repository.enroll`, `project.configure`, `profile.put`, `plan.put`,
`plan.reorder`, `task.criteria.revise`) — and 6.8 adds **no new product
capability**. Every command and envelope kind it exposes already exists; 6.8
builds forms over them and does not change their validation.

Depends on 6.2's screen stack, form components, confirmations and bounded text
entry. It does **not** depend on 6.5: 6.8 builds no restrictions read model of
its own; it consumes 6.4's only where the 6.4 checkpoint says to.

## Invariants 6.8 must not break

1. Every definition change is a **versioned human command** with a unique
   command ID and an expected revision. The forms must not bypass
   `Engine.Apply`, and must not mutate state by any other path.
2. `project.configure` and `plan.put` **retire pending requests** and advance the
   policy epoch. The interface must show that consequence before the change is
   committed, because it silently cancels in-flight approvals.
3. Criteria changes require explicit human revision authority. No form may make
   a criteria change as a side effect of another edit.
4. Existing tasks cannot be silently removed by a plan replacement, and
   `plan.reorder` preserves the exact task set and task revisions.
5. A profile records **credential references, never credential values**. No
   form may accept a value.
6. `--synthetic-fixture` and other gating flags stay explicit. A form must not
   pre-check a box the operator did not choose.
7. `resources reconcile` is a human **attestation**, never an automatic process
   cleanup. A dead controller is not evidence that its claims are free.
8. `--single-host` remains an explicit choice. The interface must not present
   cross-host or cross-instance coordination as available.
9. The `.vigil-disposable-fixture` marker and `runtime_kind=synthetic` gates
   stay visible where a fixture path is offered.
10. `doctor` installs nothing and launches no agent. Its screen must not offer
    an action.
11. `init` refuses overlapping registered projects and reuses a physical root
    across symlink aliases. The screen must show both outcomes as they occur.

## Work checkpoints

### A. Project creation and selection — closing 6.1-F15

- [ ] A project-creation screen: enter an absolute root, and see the result of
      the reuse/overlap checks **before** registering. Refuse an overlapping
      registered project and explain which one.
- [ ] The parent-project warning (R19): when a possible parent project exists,
      warn before registering a nested root, and make the choice explicit
      rather than defaulting.
- [ ] State-directory placement shown explicitly, with the requirement that
      state live outside every managed checkout tree and that existing state be
      private.
- [ ] Project list with each project's root, state, revision and active plan;
      switching through 6.2's screen stack.
- [ ] From a cold start with **no** project registered, the interface must reach
      a usable first screen. This is the single most important parity
      property in 6.8: today `vigil dashboard PROJECT_ID` cannot be reached
      without leaving the interface.

### B. Project configuration and policy

- [ ] A form for `project.configure`: model policy, denies, required checks,
      task/attempt limits, repair limit, supervisor profile, approval mode,
      human-acceptance requirement, review blocking severity, transcript
      retention days.
- [ ] Check definitions as a first-class sub-form: ID, exact argv array, project-
      relative cwd, sorted environment, sorted required outputs, positive
      timeout, optional output ceiling. Enforce what the CLI enforces: an exact
      absolute executable or an explicitly approved canonical `PATH`, never
      ambient lookup; `HOME`, `TMPDIR`, `TMP` and `TEMP` not overridable;
      definitions immutable within their configuration snapshot.
- [ ] Before committing, show the **consequence**: the project returns to
      `paused`, the policy epoch advances, and every pending request is
      cancelled. The operator confirms with that stated.
- [ ] An effective-policy view showing the model policy, the denies and the
      approval mode, with the origin of each value.

### C. Profiles

- [ ] A form for `profile.put`: ID, harness, version, model, provider,
      `credential_ref` as a **name**, roles, endpoint ID, local-inference and
      auxiliary-local flags, delegation-disabled, capabilities, restrictions.
- [ ] A credential-reference control that accepts only a name pattern and
      refuses a value-shaped input, with the reason shown. A form that accepts a
      secret would be a new credential-handling path, and must not exist.
- [ ] A profile list with revisions, roles, capabilities and restrictions, and
      an explicit statement that declaring a profile **does not** qualify a
      route, version or containment. R42 and P01.
- [ ] Show which closed runtime gates still block a profile from being
      qualified, with the exact issue text.

### D. Specifications, plans and tasks

- [ ] `spec-import`: an owned, non-symlink `.md` file inside the registered
      project root, 1 byte to 64 KiB; show the published content-addressed
      revision and its exact content. Refuse a path outside the root and say so.
- [ ] `spec-show`: the exact verified revision and content, with the
      instruction that the content is untrusted text.
- [ ] `plan.put` as a guided editor: plan metadata, quality criteria, quality
      checks, reviewer profile, human-acceptance requirement, and the task set
      with objective, criteria (including which are manual), dependencies,
      context, scope, checks, questions, implementation and reviewer profiles,
      difficulty, rationale, active limit and repair limit.
- [ ] Live validation as the operator edits: dependency cycles, missing
      required task fields, unresolved questions, missing profiles,
      unapproved specifications, dependency acceptance, and policy
      constraints. Show each as a readiness issue **before** commit, not as a
      refusal afterwards.
- [ ] Show the exact envelope that will be applied, so the operator sees what
      the versioned command contains.
- [ ] `plan.reorder` preserving the exact task set and revisions, with the
      resulting order previewed.
- [ ] `task.criteria.revise` as a distinct, explicitly authorized action with
      its reason, never as a side effect of another edit.
- [ ] `proposal-create` as a guided editor over the same task structure, with
      the resulting proposal's approval request and its clarification items
      created and shown. `proposal-show` renders the exact immutable revision.
- [ ] Manual prerequisites per task, with `satisfied` and non-empty `evidence`
      when satisfied, and the readiness block when not.

### E. Repositories

- [ ] `discover` as a view: existing nested Git roots, canonical and common-Git
      identities, HEAD commit and ref, gitfile layouts, and the explicit
      unsupported/unborn issues. State on screen that discovery is read-only
      and enrolls nothing.
- [ ] `repository.enroll` as a guided form: ID, plan, root, base ref, plan
      branch, dirty-work choice (`clean`, `include` with exact included paths,
      or `postpone`) and nested boundaries chosen from the `discover` output.
- [ ] For the dirty-work choice, show the uncommitted paths discovery found and
      require an explicit per-path decision. R40: never delete them
      automatically. State that included and postponed work is recorded but
      cannot be executed by this slice.
- [ ] Refuse a credential-bearing remote URL, visibly, with the reason.
- [ ] `repository` as a view: identity, base ref, plan ref, baseline and current
      dirty state.
- [ ] `prepare-repository`: show the exact clean fingerprint and the selected
      base being required, that it creates or reuses **only** the recorded ref
      and symbolic HEAD, and that it never checks out over edits. A crash is
      reconciled from the observed exact ref — show that path.

### F. Resources and coordination

- [ ] `resources endpoint` as a form: physical endpoint ID, URL aliases,
      capacity, and the explicit `--single-host` choice. State that aliases
      belong to one physical endpoint, not separate capacities, and that Vigil
      does not start the service.
- [ ] `resources status` as a coordination view: physical endpoints, owners,
      owner IDs, fencing generations, claims, tickets, slots, waiting requests
      and the quarantine state. This is the surface R71 and R60 require and the
      interface currently has none of.
- [ ] State the boundary plainly on the screen: coordination is host-local, and
      external clients or other machines cannot be assumed to honor these slots.
- [ ] `resources reconcile` as a **human attestation**: the dead owner ID, the
      observation text, and a statement that this is the operator's assertion,
      not an automatic cleanup, and that a dead controller is not evidence that
      its claims are free.

### G. Boundary diagnostics

- [ ] `doctor` as a read-only view with no actions: execution-boundary
      prerequisites, each missing prerequisite named. P02's "an unavailable
      executable or unsupported operation has an explicit explanation".
- [ ] A permanent panel listing the production gates that remain closed —
      trusted execution qualification, live model qualification, reviewer
      qualification, production delivery — with the exact issue text, so a
      human looking at the primary interface can see precisely what is not
      enabled. R70's honesty requirement, and the reason no interface claim of
      "it works" is available yet.

## Autonomy and user gates

Autonomous: all of it. Every form operates on a disposable fixture with
credential references, never values, and the `discover`/`repository`/
`resources` paths are entirely local.

User gates: choosing real profiles, real model policy and real spending ceilings
is a human setup choice and is **not** made by this stage. Real endpoint
capacity claims, real host coordination and native macOS evidence remain open.
