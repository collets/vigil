## The 5.7-F1 fix

The accepted harness then found a way to reach the delivery path at all, which
exposed that the blocking finding was two independent product contradictions rather
than one, plus a consequence neither had reached. The fix is in
`internal/core`: the checked-out-plan-ref refusal is now conditional on the
application not owning that checkout, the accepted repository state is honoured
once this plan's own verified delivery commit has recorded it, and the operator's
index is refreshed for exactly the committed paths when the application moved the
ref HEAD points at.

**This re-opened the accepted Stage 5.2/5.6 delivery slice.** That is a deliberate,
authorized exception to the stage order, recorded because it changes the behaviour
of an independently accepted slice and must be reviewed on its own terms.

The review of that fix returned **conditional with no P0 and no P1**: neither
relaxation could be broken. What it did find was that the acceptance argument was
weak — four of the five guards in the archive relaxation, and three of the four
conditions in the ownership predicate, could each be removed with the entire
`internal/core` suite green. In a re-opened accepted boundary that is the finding
that matters, so each guard now has a test that only it can catch. Two of those
tests are worth their own note:

- **A guard that turned out not to be independently load-bearing.** The content
  digest is deliberately redundant with the dirty flag: `Dirty` is Git's own
  comparison of the index against the head tree, the worktree against the index,
  untracked files and abnormal index entries, so everything the digest can see it
  already reports. An attempt to isolate it with an untracked file failed — the
  checkout was dirty. The guard is kept as a second opinion, and both the code and
  the test now say plainly that it is defence in depth rather than a load-bearing
  check, so nobody later mistakes it for one.
- **An ordering that looked security-relevant and is not.** The predicate reads the
  most recent branch operation for a repository revision, which looked like a way
  for a stale authorization to be chosen. A unique index,
  `one_repository_branch_preparation`, makes it impossible to have two, so the
  ordering cannot matter. The index invariant is now asserted by a test, so dropping
  it would fail rather than silently making the query order-dependent.

The review also found a false security claim in the predicate's own comment — that a
person who moves HEAD away and back stops being application-owned. It does not:
`observed_head_ref` is a stored string and is never re-read live. The comment now
states that limit instead of claiming a protection that does not exist, and names
what does bound it.

The fix is verified by tests that fail against the pre-fix behaviour:
`TestCommitProceedsWhenApplicationOwnsThePlanCheckout` and
`TestArchiveAcceptsTheAcceptedContentAlreadyRecordedByDelivery` both fail against
it.

**On "every guard is mutation-verified": read that claim narrowly.** The ninth
reviewer to check this claim falsified the earlier version of it — of the nine guards
in the two relaxations, three were not load-bearing, and two of the three were
*unpinned in a way that hid a real hole*: the parent guard's test read the recorded
head before creating the commit it meant to record, and the repository-revision test
queried with a branch the revision filter never had to match. Removing the revision
filter let a **superseded** repository revision confer ownership. Both are fixed, and
the fixed tests assert their own preconditions — that every *other* guard passes —
so they cannot silently stop being isolating.

What is now true, and verified by mutation rather than asserted: of the nine guards,
**six are load-bearing and each fails the package when removed**, and **three are
deliberately redundant** — the content digest, the `gitOID` pre-check, and the
head-equality guard that subsumes the latter. Each of the three carries a comment in
`internal/core/repositories.go` saying it is defence in depth rather than a
load-bearing control, precisely so nobody later mistakes it for one. Two further
safety checks introduced by this slice — the live `HEAD` re-read in the index
refresh, and the enrollment guard refusing a plan branch equal to the base branch —
are also load-bearing and now caught when removed.

The six load-bearing guards are: content/ref/dirty in the archive relaxation, the
head-equality that follows, the delivery-commit parent, and the repository-revision
scope in the ownership predicate.

### Fourth review, of the third remediation

The fourth review **could not defeat the guard** across a twelve-input battery
including the symlink attack (the documented path itself symlinked elsewhere), and

- **P1 — the previous remediation made the walkthrough abort on ~60% of runs and
  reported a product defect that does not exist.** `SubmissionUnresolved` treated
  `writing` as requiring `start` to be withheld, on the reasoning that production
  "refuses to replay" a `writing` generation. Production does refuse — but in
  `Runner.submit` and `Runner.Reconcile`, which are deterministic and do not depend on where a
  kill lands. `Inspect` withholds `start` only for `uncertain`. So the harness
  asserted a property the product does not have, and because that assertion aborts,

  12 aborts in 20 runs, each exiting 1 with 19 undecided rows and reporting "an
  uncertain submission can still be resubmitted" — a fabricated blocker. The
  reviewer's reproduction is recorded here because it is the sharpest evidence in
  this slice that a safety assertion derived from the wrong layer is worse than no
  assertion at all.

  guarantees. `uncertain` is the only hard check; `writing` checks for `reconcile`
  on a run that has not finished, which cannot false-positive; a resolved state
  resolves; an absent or unrecognised state establishes nothing. The check is now
  non-fatal, so a racy landing that fails it is recorded as a limitation rather
  than asserted. **Verified:** 14 of 14 runs exit 0, and both landings were
  observed in the sampling, so the fix is not luck.

The sixth review **accepted the harness** — "sound enough to stop iterating on the
enforcement gaps" — and confirmed the central property is now enforced in three
independent places it could not break. It re-verified all six prior claims and
produced its own mutations of the drift guard, which is where that review earned

text-shape heuristic on one file, and that it **missed five of six realistic
production mutations**, including a `uncertain`-offers-`start` replay-safety

- **The false sentence was narrowed, not eliminated.** Keying the clause off
  `run_state == "completed"` rather than off the observed command list made it

### Seventh review, and why this is the last one

The seventh review judged the **harness sound** and stated that further review
rounds no longer add value, which is the finding that ends the loop. It
independently mutated the drift guard 17 ways and caught 15, including all three
mutations the previous review had shown the older guard missed. It also found two
silent holes in the *new* parser, and one of them was mine: the schema guard read
only `CREATE TABLE runs (`, so a widening of `runs.state` shipped through the
repository's own rebuild idiom — `CREATE TABLE runs_v<N>` plus
`ALTER TABLE … RENAME TO runs`, which is the only shape SQLite permits, since it
cannot `ALTER TABLE … ADD CONSTRAINT` — passed with the suite green, while the
results document claimed it could not. Closed as follows:

- **The rebuild idiom is now handled, and the claim is now true.** The table
  reader matches a versioned rebuild only when it is actually renamed onto the
  name, so a widened `CHECK` is caught and an abandoned `runs_v2` is not reported
  as states the product can hold. Both directions were verified by mutating a
  migration. The results document was corrected to describe what the guard does
  rather than what it was hoped to do.
- **A `case` arm that assigns nothing was invisible.** Only arms that assigned
  `AllowedNext` were collected, so an early-returning arm left the count
  unchanged and the test passed. Every arm is now recorded, with a nil command
  list, and a second switch that also assigns is no longer invisible either.
- **The `undecided` class itself was unguarded.** Removing it entirely left all
  three renderer tests green, because a count of zero contributes nothing to the
  arithmetic — the same hole as the class it was added to fix. It is now pinned
  against the aborted-run state it exists for.
- **Two comments were stale, including one the previous commit had already
  corrected elsewhere.** The `writing` requirement's doc comment still stated the
  superseded "any run that has not finished" rule, and the transcription comment
  still claimed the test could not catch a production change that it now does
  catch. Both were updated, and the transcription comment now also states what the
  guard does not cover: it does not read `runner.go`, so a regression in the
  `Runner.submit` the report cites is outside it.
- **The narrowing is on the record.** Keying the `reconcile` requirement off the
  observed list means a regression withholding `reconcile` from a run that offers
  no `start` is not caught. That is a deliberate trade — the property that matters
  is on the run where a replay is possible, which is the landing this walkthrough
  actually produces — and it is written down in the code rather than left to be
  discovered later.
