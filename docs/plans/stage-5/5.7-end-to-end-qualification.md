### Second review, of the remediation

The follow-up **confirmed the P1 fix is real and genuinely closed**, verified
under test rather than by reading: the tags match production `RunView` exactly,
an empty or identity-less inspection fails rather than reads as safe, and a
regression offering `start` after a stop is now caught where the old code could
not catch it. It also confirmed the `unmet` class, the four partial markings, the
R09 gate, the opt-in wording and both documentation obligations. It then found
that the remediation itself had introduced four defects, now fixed:

- **P2 — a case detail contradicting its own observed values.** The
  controller-kill detail claimed the kill "landed after the submission was
  journaled" while the values it printed showed `submission_state=not_attempted`
  and `run_state=prepared`, and `describeKill` asserted the same thing whenever
  the kill succeeded. Where the kill lands is a race against the synthetic
  driver's speed, so the detail is now written by `controllerKillLanding` from the
  observed durable state, and never asserts a boundary it did not observe. The
  genuinely uncertain case remains carried by the Stage 5.2 crash matrix.
- **P2 — three requirements classified against the wrong text.** R41, R42 and R69
  had details about unrelated subjects: R41 is about ending delivery at draft
  creation, R42 about manually configurable profiles, R69 about managing only
  application-launched sessions. Each detail now describes what the run actually
  observed for *that* requirement, and the corresponding `gates` entries, which
  the `automated` branch had been shadowing, are removed.
- **P2 — a false claim in place of a false claim.** The first remediation's
  `sourceMentionsRequirement` tested for the requirement identifier in the cited
  record. The predecessor records are narrative documents keyed by slice-local
  finding IDs, so all 14 substantively valid citations were demoted behind the
  false blocker "no accepted record covers this requirement". The check is now a
  resolution test — the named record must be readable — which cannot demote a
  valid citation, and the results document says plainly which check was made and
  why it is not a textual one.
- **P3 — a guard that could be defeated.** The `SCENARIO_ROOT` guard used a glob
  that matched a `..` suffix, so `SCENARIO_ROOT=/tmp/vigil-stage-5.7-scenario/../../tmp/x`
  reached the `rm -rf`. The guard now rejects any traversal component and compares
  the **resolved** path against the exact documented directory. Both bypass
  attempts are rejected and the sentinel directory survives.

### Third review, of the second remediation

The third review **confirmed the guard fix is real and could not be defeated**
across a twelve-input battery, and **confirmed the P1 fix is untouched and still
fail-closed**. It also verified there was no silent reclassification (49 + 14 + 8

hide a human gate. It returned **rejected**, finding the four remediations only
partially closed and two new P2s. Now fixed:

- **P2 — the kill landing still misreported `writing`, and the detail
  contradicted its own values.** `controllerKillLanding`'s default branch claimed
  "no effect occurred" for any state it did not name, and `writing` — the
  in-flight state, which production itself refuses to replay — fell into it,
  producing a detail that said "no effect" beside quarantined workspace claims and
  an unconfirmed writer. The function now switches exhaustively over the observed
  `submission_state`, and `writing` is described as in-flight and possibly already
  delivered, with the held resource state cited as the confirmation that effects
  did occur.
- **P2 — a branch still asserted an unobserved boundary.** The `delivered` branch
  claimed "the outcome is known and no start is offered" without deriving either,
  and for `run_state=starting` production *does* offer `start` — producing one
  sentence containing both "no start is offered" and "offers … start". The safety
  reason in `forbidsUncertainReplay` is now derived from the observed state and
  cites it, and `SubmissionUnresolved` treats `writing` as unresolved, matching
  production, instead of only `uncertain`.
- **P2 — a shell-injection hole in the guard this commit had just hardened.** The
  guard interpolated `SCENARIO_ROOT` inside single quotes, so a `'` in the value
  executed *before any check ran*, and both `scenario` and `scenario-clean` then

  unreachable and a citation repointed to a wrong-but-existing record would pass.

- **P4 — coverage gaps.** `controllerKillLanding` had no test, so a table test over

  evidence class that appears in the gap list, and `RequireComplete` refuses a
  partial row that does not state what was not observed. The guard gained
  `make scenario-guard-check`, which exercises the refusal battery automatically
  rather than by hand.

### Fourth review, of the third remediation

The fourth review **could not defeat the guard** across a twelve-input battery
including the symlink attack (the documented path itself symlinked elsewhere), and
**confirmed the new tests genuinely pin the behaviour** by checking each against
the previous commit's diff rather than only against the new code. It returned
**rejected**, and its central finding is the most serious defect this slice has
produced:

- **P1 — the previous remediation made the walkthrough abort on ~60% of runs and
  reported a product defect that does not exist.** `SubmissionUnresolved` treated
  `writing` as requiring `start` to be withheld, on the reasoning that production
  "refuses to replay" a `writing` generation. Production does refuse — but in
  `Submit` and `Reconcile`, which are deterministic and do not depend on where a
  kill lands. `Inspect` withholds `start` only for `uncertain`. So the harness
  asserted a property the product does not have, and because that assertion aborts,
  a racy kill landing turned into a coin flip on the slice's entire deliverable:
  12 aborts in 20 runs, each exiting 1 with 19 undecided rows and reporting "an
  uncertain submission can still be resubmitted" — a fabricated blocker. The
  reviewer's reproduction is recorded here because it is the sharpest evidence in
  this slice that a safety assertion derived from the wrong layer is worse than no
  assertion at all.
  **Fixed:** `verifiesReplayBoundary` is written from what `Inspect` actually
  guarantees. `uncertain` is the only hard check; `writing` checks for `reconcile`
  on a run that has not finished, which cannot false-positive; a resolved state
  resolves; an absent or unrecognised state establishes nothing. The check is now
  non-fatal, so a racy landing that fails it is recorded as a limitation rather
  than asserted. **Verified:** 14 of 14 runs exit 0, and both landings were
  observed in the sampling, so the fix is not luck.
- **P2 — the summary's own arithmetic no longer reconciled.** Making `partial` a
  distinct class left it out of the printed counts, so the tool printed
  `recovery total=20 automated=11 reused=2 pending=0 unmet=3` — 16 of 20, with the
  four partial rows absent from the line entirely. The very property the class
  exists to provide, "the report can never quietly omit one", was violated by the
  report. Every class is now printed and each section's total reconciles.
- **P3 — an empty state was reported as resolving the outcome.**
  `!SubmissionUnresolved()` was true for `""` and for any future value, so an
  inspection whose `submission_state` failed to decode — for instance because the
  field was renamed in production — was declared safe *with the reason
  "submission_state=\"\", which resolves the outcome"*. `decodeIsReadable` now
  requires `submission_state`, and an unrecognised state is reported as not
  interpreted.
- **P3 — the `writing` landing claimed the resource journal.** Its text said "the
  held resource state below confirms effects did occur", but the function receives
  only the inspection, and the caller explicitly handles the held state being
  empty. The claim is removed and a test now fails on any mention of the resource
  journal in that function.
- **P3 — a disclosed gap was still filed as a pass.** R41's detail said its
  boundary was not exercised, while the row stayed `automated` and counted among
  the passes. Disclosure in prose is not a class. R41 is now `partial`, the
  requirement section joins the completeness check, and requirement gaps are
  reported under their own `requirement_gaps` key.
- **P4 — two dead and false comments, and two Makefile gaps.** A stranded comment
  still claimed `MarkPartial` kept rows in the automated class; a dead
  `UncertainSubmission` carried the claim that `uncertain` was "the only state in
  which the production path must refuse to offer start", which is the proposition
  the P1 contradicted. Both removed. `SCENARIO_COMMIT` was still interpolated raw
  into the recipes — the same injection class the guard fix had just closed, one
  variable over — and now travels through the environment like `SCENARIO_ROOT`.
  `scenario-guard-check` was missing from `.PHONY`, so a same-named file in the
  working directory would have made it silently succeed without running anything.
- **P4 — the tests were self-referential on the one point that mattered.** All
  three new tests pinned the harness's own rule; none tied that rule to what
  production's `Inspect` returns, which is precisely the gap the P1 fell through.
  `TestReplayBoundaryAgreesWithProductionInspect` now transcribes production's
  switch and requires the harness to accept every combination the product can emit.

### Accepted review, of the fourth remediation

The fifth review **accepted the commit** with no P0, P1 or P2, and independently
reproduced the stability claim: 17 of 17 runs exit 0 with `aborted: false` and
40/40 assertions, against the 8 of 20 the review before it measured. It verified
all three section totals reconcile exactly, confirmed R41 is `partial` and appears
in `requirement_gaps` in every run, and confirmed the stored gap list never drifted
from the rows.

It also closed the remaining enforcement gaps rather than deferring them, and two
of them are worth recording as findings in their own right:

- **The fix for R41 was applied to the requirement row and not to the recovery row
  it was derived from.** A controller kill whose replay-boundary check fails was
  recorded as `automated` and absent from the gap list, with the failure visible
  only in the limitations text — the identical "disclosure in prose is not a class"
  mistake, one file over. A run that fails the check is now `partial`. The branch
  was not reachable in 17 runs, so the severity was classification discipline
  rather than an observed false statement; the reviewer said so plainly, and that
  is the right way to weigh it.
- **The summary renderer had no test at all.** `cmd/vigil-scenario` had no test
  file, so the P2 defect class — a class silently omitted from the printed line
  while the suite stayed green — had nothing stopping a recurrence. The renderer is
  now a testable function, and `countLine` cannot print a total its own printed
  classes do not sum to: an unprintable class renders an explicit `UNPRINTED=`
  contradiction rather than a summary that quietly does not add up.
- **The transcription's comment claimed the test would fail if production changed.
  It could not.** A stale table would still have passed, and the enumeration mixed
  in a run state the schema does not admit while omitting five it does. The
  comment now says plainly that this is a hand-written copy whose value is that a
  reviewer has the product's rule beside it in executable form, the enumeration
  comes from the schema's actual constraint, and a drift guard re-reads the
  production source.
- **Two smaller ones.** The `writing` success reason claimed production offers
  `start` for a `completed` run, which it does not; the claim is now derived from
  the observed command list. `RequirementGapList` was stored once when a stage
  filled it in, so a stage added later would emit a list contradicting its own
  rows; it is now derived where the case gap list is derived, at the same point.
